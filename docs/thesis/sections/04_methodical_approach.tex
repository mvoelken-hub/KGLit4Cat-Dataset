This chapter derives the requirements and evaluation design for the proposed workflow.

\section{Workflow Architecture}
\label{sec:workflow_architecture}

The workflow developed in this thesis addresses the conversion of heterogeneous catalysis-related research data packages into structured, semantically enriched metadata. Its starting point is the observation that experimental data only becomes reusable when it is accompanied by contextual information about the investigated material, the data-generating activity, the analytical method, relevant parameters, units, files, and provenance. In current catalysis research, this context is often distributed across semi-structured instrument exports, descriptive text files, tabular metadata, images, and nested archive structures. Manual metadata creation can in principle recover this context, but it is time-consuming, inconsistent, and unlikely to scale to routine research-data management. Consequently, the workflow is designed as an automated assistance system that extracts candidate metadata from existing dataset packages and projects it into a controlled metadata profile. This follows the broader FAIR-oriented motivation of catalysis data infrastructures, where structured metadata and shared vocabularies are prerequisites for reproducibility, interoperability, and downstream data-driven analysis \cite{mendes2025data,schumann2025nomad,nfdi4cat2024whitepaper}.

A central design decision is that the extraction is not implemented as a single large prompt. A monolithic prompt would have to contain the task description, target schema, raw file contents, vocabulary descriptions, graph context, and the requested output representation at the same time. This is unsuitable for the present use case because dataset packages may contain multiple files and because semantic grounding requires additional context from controlled vocabularies. Even when a model offers a comparatively large context window, the useful context must be shared between source evidence and external semantic resources. The workflow therefore decomposes the overall task into smaller stages that can be executed, inspected, repeated, and validated independently. The resulting architecture is a staged extraction and enrichment pipeline. The input is a dataset archive, which is first unpacked into individual file entries. Text is extracted from files where possible and retained together with file-level provenance. The extracted files are then ranked according to their expected relevance for metadata extraction. This ranking step is necessary because research data packages often contain a mixture of descriptive metadata files, instrument files, processed data, images, and raw measurements. Context-rich files such as descriptions, manifests, method files, reports, and compact processed tables are therefore processed before files that are unlikely to contain metadata.

After ranking, the textual content is split into semantic chunks. The purpose of chunking is not only to reduce prompt size, but also to preserve local topical coherence. Long technical files frequently contain blocks for different acquisition parameters, processing settings, sample information, and instrument configuration. Treating the entire file as one prompt would obscure this internal structure, whereas fixed-length chunking could cut through meaningful parameter groups. The workflow therefore uses semantic chunking based on embedding distances between neighboring text windows. Low distance indicates that adjacent lines likely belong to the same topical region, while high distance is interpreted as a potential internal boundary.

Each chunk is then processed by a Large Language Model (LLM) to produce an intermediate extraction context. This intermediate representation is intentionally separated from the final metadata profile. It records the extracted data-generating activities, methods, evaluated entities, agents, resources, quantitative attributes, and qualitative attributes before they are forced into a specific application profile. This separation reduces coupling between source interpretation and output formatting. It also makes the workflow more inspectable: errors can be attributed to chunking, extraction, profile construction, semantic reconstruction, or final vocabulary grounding instead of being hidden inside one end-to-end generation step. Similar LLM-based extraction approaches have shown the practical value of prompt-driven extraction from heterogeneous catalysis literature, but the present workflow adapts this idea to dataset-level metadata packages and combines it with vocabulary-backed normalization \cite{walls2025catminer}.

The merged evidence context is first projected into a selected application profile. Profile construction creates an initial draft, improves evidence-backed field coverage, evaluates semantic requirements, reconstructs misplaced objects where possible, and validates the result against the profile schema. This profile-oriented architecture is aligned with the idea of DCAT-AP Plus and ChemDCAT-AP-style metadata profiles, where general dataset-level metadata is extended by domain-specific context about scientific data generation \cite{stroemert2026chemdcat}. The profile therefore determines where extracted entities, activities, agents, and attributes belong before vocabulary identifiers are assigned.

The last enrichment stage is controlled-vocabulary grounding over selected fields already placed in the finalized profile draft. Quantitative attributes are normalized against quantity-kind and unit vocabularies, while qualitative terms such as methods, materials, instrument parts, and domain concepts are matched against chemistry- and catalysis-related vocabularies. This stage retrieves a constrained candidate set through vector similarity, lexical full-text search, and local graph expansion; the LLM selects a suitable candidate or leaves the field unresolved. The application profile answers where information belongs, whereas vocabularies answer which concept or unit a placed value denotes. Candidate sets, selected URIs, and unresolved cases remain auditable workflow artifacts.

The workflow boundary is deliberately limited to metadata extraction and semantic enrichment. It does not claim to fully interpret every scientific file format contained in a dataset package, nor does it replace domain-expert validation. Binary files, rendered images, spectra, and other non-textual resources may be retained as dataset resources even when their internal content is not directly interpreted. The primary output of the workflow is therefore a structured metadata proposal with traceable source evidence and vocabulary mappings. This proposal can be inspected, corrected, and evaluated against a manually curated reference in the evaluation chapter.

From an architectural perspective, the workflow separates four concerns. First, source handling converts a heterogeneous archive into ordered, text-accessible evidence units. Second, extraction converts local evidence into a domain-neutral intermediate representation. Third, profile construction places evidence-backed objects in the target metadata schema and validates their structure and semantic ownership. Fourth, final semantic grounding connects selected placed values to controlled vocabularies and records the matching process. This separation supports modular evaluation: object extraction, value extraction, schema validity, URI mapping, and traceability can be assessed independently. It also leaves room for future extensions, such as replacing the chunking strategy, adding file-format-specific parsers, changing the LLM backend, or introducing additional application profiles without redesigning the complete workflow.
