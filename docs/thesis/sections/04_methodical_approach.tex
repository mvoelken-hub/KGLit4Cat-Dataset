\label{chap:methodical_approach}

This chapter describes the methodical approach used to construct semantic metadata from heterogeneous dataset packages.
The workflow is designed as a staged extraction process.
It does not treat the uploaded dataset as one large input.
Instead, it separates source access, preprocessing, evidence extraction, profile construction, vocabulary grounding and curation.
\Cref{fig:workflow-concept} shows this process on a conceptual level.

The workflow starts with the ingestion of a dataset package.
The package is not manually rewritten before processing.
This keeps the input close to the form in which it would appear in a repository or laboratory export.
The only practical requirement is that relevant information must be available in files that can be decoded or converted into text.
The text-accessible files are preprocessed and denoised before they are split into smaller chunks.
In parallel, the workflow creates a dataset-level overview from the package structure and from compact per-file summaries.

The individual chunks are then processed by an \ac{LLM}.
The model extracts metadata signals that are grounded in the source text.
These signals are not yet placed into a specific metadata profile.
They form an intermediate evidence representation.
This design follows the \ac{GO} approach, in which information extraction is separated from the organization of this information into a target schema \cite{li2024structuredoutput}.
After the chunk iteration, the extracted signals are merged and deduplicated.
The result is an evidence grounding set for the profile construction stage.

The workflow then initializes a dataset-level \ac{DCAT-AP+} artifact.
This artifact provides the target structure for the extracted metadata.
The schema is filled through a requirement-driven procedure.
The workflow checks which requirements are already supported by the evidence and which requirements remain unresolved.
Resolvable gaps are patched from the evidence grounding set.
Unresolved requirements are flagged for manual curation.
After curation, the workflow queries a property graph of controlled vocabularies.
This maps selected \texttt{DefinedTerm} shapes in the \ac{DCAT-AP+} artifact to suitable concepts and classes through \texttt{dcterms:type} or \texttt{rdf:type}.
The final artifact is exported in an \ac{RDF} compatible form.

\section{Dataset}
\label{sec:dataset}

The workflow is intended for heterogeneous dataset packages that contain text-accessible files.
It is therefore not tied to one file extension or one instrument format.
At the same time, it does not claim semantic access to every binary or visual resource.
Binary files and images can be retained as package resources, but they only contribute to extraction when their relevant content can be represented as text.
This boundary is important for instrument exports, because they often combine raw signals with textual parameter files.

This study used \ac{NMR} datasets as test datasets.
One sample is presented in \cref{fig:1H-NMR-dataset} to show the type of resources these packages contain.
The sample dataset consists of a single one-dimensional \textsuperscript{1}H NMR dataset exported from ChemSpectra, a web-based spectra editor for analytical data \cite{Huang2021}.
Within this export, the nested archive \texttt{10.zip} preserves the native output from a Bruker \ac{NMR} system.
Bruker is the instrument and software environment from which the raw export originates in this example \cite{brukerTopSpin}.
The archive is therefore treated as an example for a raw instrument generated input for the metadata-extraction workflow.
It contains the acquired \ac{FID} signal together with the associated acquisition parameters.
In contrast, the accompanying files generated by ChemSpectra represent a standardized spectral representation in the \ac{JCAMP-DX} format.
Using both the raw and standardized files as input separately allows the workflow to be evaluated on both types of data, which are expected to be present in real-world datasets.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.8\textwidth]{figures/1H-NMR-dataset.png}
    \caption{Sample \textsuperscript{1}H NMR dataset with its file contents.}
    \label{fig:1H-NMR-dataset}
\end{figure}

The contents of \texttt{10.zip} are mostly text-accessible files.
The archive also contains the binary file \texttt{fid}, which stores the acquired time-domain signal.
This file is important as a research object, but it contains primary data rather than textual metadata.
The surrounding Bruker files carry the metadata that make this signal interpretable.
Most of these files are plain text files.
Once their character encoding has been identified as \ac{ASCII}, they can be read without further conversion.
The textual files describe the acquisition and processing context of the spectrum.
They contain Bruker parameter files with \ac{JCAMP-DX}-style records, Bruker-specific acquisition settings, processing settings for the derived spectrum, and the selected pulse sequence.
Other records document the processing history produced by Bruker TopSpin, the software environment used to acquire and process Bruker \ac{NMR} data \cite{brukerTopSpin}.
They also describe instrument configuration, spectrometer settings, shim values, and a short human-readable sample title.
Some files mainly contain numeric frequency values.
These values can be relevant for signal processing, but they provide little natural-language metadata for the extraction task.

The ChemSpectra export contains one text-accessible file that is especially relevant for extraction.
The \texttt{10.edit.jdx} file is a \ac{JCAMP-DX} link file whose main block represents the \ac{NMR} spectrum as \texttt{XYDATA}.
It records the observed nucleus, observation frequency, solvent, shift reference, pulse sequence, axis units, scaling factors, chemical-shift bounds, and point count.
The same file also contains ChemSpectra-derived integral and peak-table blocks, including edited and automatically detected peaks.
Most lines, however, encode spectral values or peak coordinates rather than descriptive metadata.
For the workflow, this file therefore represents a standardized but dense text input in which useful key-value records must be separated from long numeric arrays.

These different datasets structures are useful test cases for the workflow.
They differntiate between metadata signals that are embedded in one dense text file together with the primary data and metadata signals that are distributed across multiple files in a nested archive.
The workflow must therefore handle the separation of metadata from primary data, the extraction of key-value records from noisy text, and the preservation of file provenance for correct scoping of signals.

\section{Preprocessing}
\label{sec:preprocessing}

The ingestion stage expands the uploaded archive and records the contained files as package resources.
Nested archives are expanded recursively.
This preserves the original package structure while making individual files addressable by later workflow stages.
Each file is then handled according to its accessible content type.
Plain text files are decoded after character-encoding detection with the \texttt{charset-normalizer} library \cite{charsetNormalizerDocs}.
Tables are linearized into textual rows.
PDF files are processed by text extraction.
Images and unsupported binary files are kept as resources, but they are not treated as textual evidence.

After text extraction, the workflow applies a line-level text-quality gate.
The gate classifies each extracted line as either kept or dropped using deterministic heuristic rules.
Empty lines, one-character lines, lines with many control characters, repeated-character noise, and dense numeric arrays are removed directly.
The numeric-array rule is applied before scoring so that long lists of signal or frequency values are not passed to later model stages.

All remaining lines are scored from textual and structural features.
Positive evidence is assigned to lines that contain multiple words, sufficient alphabetic content, whitespace, reasonable word length, or recognizable structured metadata syntax.
The latter includes short key-value records, assignment-style records, headings, and bullet-like entries.
This structured-text signal is important for instrument files, because acquisition and processing metadata are often stored as compact parameter records rather than prose.

The score is reduced for lines dominated by digits or symbols, dense strings without whitespace, very long uninterrupted tokens, and hexadecimal-like values.
These features are detected with regular-expression patterns and character-level statistics and are translated into additive score contributions.
Textual and structured metadata features add to the score, while noise-like features subtract from it.
A line is kept only if this final score reaches the configured threshold.
Before the drop decision is applied, users can manually protect individual lines in the preview.
Protected lines are retained for downstream chunking even if the heuristic gate would otherwise classify them as noise.
The gate parameters are also exposed in the interface.
Users can adjust the symbol-ratio threshold, digit-ratio threshold, minimum keep-score threshold, and structured-text bonus.
These controls make the filtering behavior tunable so preprocessing can be adapted to different types of instrument files.
This design removes low-information technical noise while preserving readable metadata records, including Bruker-style parameter lines that contain symbols, numbers, or key-value syntax.

\Cref{fig:text-quality-gate} shows the corresponding preview in the workflow interface for the Bruker acquisition-parameter file \texttt{10/acqu}.
The preview reports the selected file, the total number of source lines, the number of filtered lines, and the number of protected lines.
Each line is displayed with its gate decision, and individual lines can be protected before filtering is applied.
Kept lines are shown as readable parameter records, and the decision tooltip exposes the final score together with the feature labels that contributed to it.
The interface also exposes the main gate parameters, including the symbol-ratio threshold, digit-ratio threshold, keep-score threshold, and structured-text bonus.
In the example, the header records and Bruker parameter assignments are kept even though they contain symbols and numeric values.
By contrast, dense numeric array lines are marked as \texttt{DROP}.
The figure therefore illustrates that the gate removes low-information numeric content while preserving structured acquisition metadata for downstream chunking and allowing manual protection where needed.

\section{Dataset-Level Overview}
\label{sec:dataset_level_overview}

After the preprocessing steps, the workflow creates a dataset-level overview before chunk evidence is extracted.
This stage consists of several smaller orientation steps.
First, the program creates bounded previews from text-accessible files.
Small files are represented as complete text.
Larger files are represented by sampled windows from the beginning, middle, and end.
The previews keep the prompt size controlled and are used by the \ac{LLM} to produce compact file-local summaries.
The summaries describe the explicit file purpose when it is visible.
They also describe the nature of the information in the file in short natural-language form.
They do not split the content into provenance, software, setting, or numeric signal fields.
They do not enumerate all parameters and do not replace the source text.
After that, the files are ranked according to their expected relevance for metadata extraction.
The ranking is a deterministic heuristic.
It scores the natural-language summaries for broad metadata-relevant terms and combines this with simple file-path, extension, and size indicators.

The workflow then builds a dataset graph from the ranked file context.
The graph is first seeded programmatically.
Directory and file nodes are derived from archive paths, and deterministic containment relations are added.
Additional group nodes indicate recurring dataset roles based on the validated file summaries.
These roles include acquisition settings, processing settings, audit information, instrument configuration, or raw data.
The \ac{LLM} then proposes a structured overview from the seeded graph and the ranked summaries.
The result is sanitized programmatically so that it only refers to files present in the package.
The resulting graph overview is stored as orientation context for later workflow stages.

\Cref{fig:initial-overview-graph} shows the dataset-level overview generated for the \textsuperscript{1}H NMR sample dataset.
The graph uses color to distinguish node types.
The green central node represents the dataset root.
Purple nodes represent subdirectories and inferred group nodes.
Subdirectory nodes are connected to file nodes through containment relations, while group nodes represent recurring metadata roles such as acquisition settings, processing settings, instrument settings, audit information, and raw data.
Blue nodes represent individual files.
They contain file-local summaries and are linked both to their directory context and to relevant group nodes.
The links from file nodes to group nodes indicate that a file documents a particular type of metadata.
The selected file \texttt{10/acqu} is shown in the detail panel on the right.
Its rank and summary indicate why it is considered relevant for metadata extraction: it contains acquisition parameters for the Bruker \textsuperscript{1}H NMR experiment, including pulse-sequence, frequency, and data-acquisition information.
The figure therefore illustrates how the workflow turns file-local summaries into dataset-level orientation context before chunk-level evidence is selected.

\section{Chunking}
\label{sec:chunking}

Chunking manages the amount of text that is passed to later \ac{LLM}-based workflow stages.
Its purpose is to compensate for the limited context window of \acp{LLM}, as described in \cref{sec:large-language-models}.
Reducing the context size is beneficial for two reasons.
First, it supports the use of locally deployed models, where memory and compute constraints make smaller inputs more practical \cite{xu2024ondevice}.
Second, it reduces the need to perform extraction over very long inputs.
Long-context studies show that models do not use long prompts uniformly and that realistic long-context reasoning remains difficult even for capable systems \cite{liu2024lostmiddle,bai2025longbenchv2}.
Chunking also keeps source provenance local.
Each chunk retains its file path and the line span from which it was produced.
This allows later evidence claims to be traced back to the corresponding source location.

Two chunking strategies are used in the prototype.
The semantic strategy was tested to reduce the risk of splitting related parameter records only because a fixed token limit has been reached.
This matters for files in which several neighboring lines are only interpretable together.
The strategy creates sliding windows over the retained text lines and uses an embedding model to represent each window as a vector.
It then calculates the cosine distance between consecutive window embeddings.
Large distances indicate stronger changes between neighboring text regions.
The highest distances are therefore treated as candidate breakpoints.
The resulting chunks are intended to preserve locally coherent spans, but the breakpoint selection itself is still a heuristic preprocessing step.

The fixed-token strategy follows a simpler deterministic rule.
It chooses a target number of tokens per chunk and fills each chunk until this target would be exceeded.
The split is independent of content similarity.
This makes the strategy faster and easier to reproduce, but it can separate lines that belong together semantically.
In the test dataset, fixed-token chunking finishes in a few seconds, whereas semantic chunking can take substantially longer because it requires embedding requests for many line windows.
Both strategies apply minimum and maximum token limits after the initial split.
The method therefore treats chunking as context management and provenance preservation, not as a final semantic interpretation of the source files.

\section{Evidence Extraction}
\label{sec:evidence_extraction}

The evidence extraction stage iterates over the prepared chunks.
Its purpose is to turn local source text into explicit evidence signals before these signals are organized into the target metadata profile.
This follows the \ac{GO} principle of separating content generation from content organization \cite{li2024structuredoutput}.
The stage captures observations that may later support dataset identity, resources, methods, instruments, software, activities, measured values, conditions, or surrounding provenance.

For each chunk, the \ac{LLM} receives the current chunk text and chunk metadata.
The chunk metadata contains the package name, file path, and line span.
The system prompt is augmented with a compact orientation section.
This section is not the full initial overview object.
It contains a token-limited excerpt of the initial extraction overview, consisting of the graph nodes and relations around the current file.
It also contains the initial summary for the current file, selected by matching the chunk file path against the stored file summaries.
This context is supplied only to help interpret the local source text.
It must not be cited as evidence.
The model instruction asks the \ac{LLM} to extract broadly reusable metadata signals from the current chunk and to copy every supporting source span from that chunk.

The model-facing schema is intentionally small with only four fields: \texttt{category}, \texttt{role}, \texttt{claim}, and \texttt{evidence\_\allowbreak{}text}.
The \texttt{category} field describes what kind of source signal was found.
The \texttt{role} field describes how the signal may later be used by the profile construction stage.
The \texttt{claim} field states the observation in a compact and checkable form.
The \texttt{evidence\_\allowbreak{}text} field contains the copied source span that supports the claim.
The categories distinguish resource, method, measurement, condition, software, instrument, activity, surrounding, and other signals.
The roles distinguish identity, descriptor, context, parameter, qualitative attribute, and other reusable metadata.
These categories and roles are not final profile classes.
They provide a coarse routing layer that helps the later profile construction stage organize the extracted signals.

Several fields are added deterministically after generation.
The backend assigns stable candidate identifiers, file paths, line spans, source-context windows, and evidence-match scores.
It validates that the copied \texttt{evidence\_text} is supported by the current chunk.
Candidates whose copied evidence cannot be matched to the chunk are filtered out.

The remaining candidates are then reviewed by an \ac{LLM}-based critic.
The critic receives the validated candidates together with the same chunk metadata and local chunk text.
It evaluates whether each claim is supported by its copied source span.
It also assesses whether the claim is self-contained, whether its file or dataset scope is clear, and whether the signal remains meaningful outside the local runtime environment.
For each candidate, the critic returns categorical judgements for groundedness, self-containedness, scope clarity, portability, semantic interpretability, environment dependence, specificity, novelty, and ambiguity.

Routing is performed programmatically from these critic assessments and is shown in \cref{fig:evidence-critic}.
A candidate is routed as portable evidence only when the critic marks it as grounded, self-contained, semantically interpretable, and specific.
Its uncertainty must not be high, and its scope must be at least partially clear.
Portable evidence is therefore intended to provide reusable input for later profile construction.
The note should remain understandable outside the immediate chunk prompt and should be traceable back to source text.
This status is auditable rather than assumed.
Each note keeps the copied evidence text, source file, line span, local source context, route reason, and critic assessment, so later profile entries can be checked against the original chunk.
Candidates are retained as contextual evidence when they are grounded enough to remain useful but are only partially self-contained, only partially portable, ambiguous, or dependent on file-level or dataset-level context.
They are therefore not routed into the pool of queriable portable evidence, but only appear as contextual notes for portable evidence notes that have a close origin in the same file.
Therefore, contextual evidence can still support later decisions, but it is treated as weaker orientation for schema patching than portable evidence.
Rejected evidence records cover candidates whose copied evidence text cannot be matched to the chunk, candidates rejected by the critic as ungrounded, and duplicate evidence records removed during routing.
The critic model is not yet seeing the final metadata schema that the workflow aims to produce.
It provides structured quality judgements that determine how evidence candidates are retained or filtered for later schema patching.

\begin{figure}[H]
    \centering
    \includegraphics[width=0.6\textwidth]{figures/evidence-critic.png}
    \caption{Categorization of extracted evidence notes by an \ac{LLM}-critic. It receives extracted candidates from a chunk as input and returns structured judgements that lead to routing as portable evidence, contextual evidence, or rejected evidence.}
    \label{fig:evidence-critic}
\end{figure}

After all chunks have been processed, the workflow merges the routed evidence contexts from the individual chunks.
This merge preserves the distinction between portable evidence, contextual evidence, rejected evidence, and file inventory entries.
Exact duplicates are removed first.
The duplicate key combines category, role, and claim.
If several candidates share this key, the workflow keeps one representative.
Candidates from higher-ranked files are preferred.
A second duplicate pass compares the normalized evidence text of portable candidates.
Highly similar candidates are grouped, and one representative is kept for each group.
Clear near-duplicates are resolved deterministically, while less clear similarity groups can be triaged by an \ac{LLM}.
The resulting evidence grounding set forms the input for profile construction.

\section{DCAT-AP+ Artifact Construction}
\label{sec:dcat-ap-artifact_construction}

The \ac{DCAT-AP+} artifact construction stage turns the evidence grounding set into a schema valid \texttt{Dataset} resource.
It is split into smaller steps.
The workflow first creates a schema-constrained dataset draft.
It then fills and repairs this draft stepwise through profile requirements rather than through one free-form generation step.

\subsection{Draft Initialization}
\label{sec:draft_initialization}

Draft initialization creates the first \ac{DCAT-AP+} \texttt{Dataset} artifact draft.
It resolves the target shape and creates a minimal schema shell in \ac{JSON} format from the required fields.
A \ac{LinkML} generated \ac{JSON} schema artifact is used to determine the required fields for the \texttt{Dataset} shape.
The required fields are then resolved based on their data type and become empty placeholders in the draft.
It gives the draft a valid structural starting point before evidence is applied and the placeholders mark fields that can later be enriched or pruned if no evidence supports them.
After that, the fields \texttt{title}, \texttt{description}, \texttt{identifier}, and \texttt{id} are mapped to sensible default values.

For the \texttt{title} field, the evidence notes are queried for candidates with a \texttt{descriptor} role and a title-like claim formulation by matching the pattern \enquote{the dataset title is ...} or \enquote{the dataset is named ...}.
If no such signal is found, the field is not part of the initialization.
The \texttt{description} field defaults to the dataset-level summary from the earlier initial overview stage.
The \texttt{identifier} field is initialized with the data package identifier.
This \ac{identifier} is generated during dataset upload and consists of an eight-character prefix of a \ac{SHA256} hash of the package name and the contained file names.
It is used as a stable local package identifier within an extraction run.
The \texttt{id} field has a different role.
In the \ac{DCAT-AP+} design, it denotes the public identifier of the dataset as an instance node and is usually expected to be a \ac{URI} or \ac{CURIE}.
The implementation initializes this field from the same package identifier as a local dataset node reference.

After this schema shell has been prepared, an overview-level projection is performed.
This projection is an \ac{LLM}-supported step.
The model receives the schema shell with the dataset-level summary, and the ranked file summaries from the initial overview stage.
Its task is limited to shallow dataset fields.
It can propose a title, keywords, and a concept label as dataset type.
The prompt instructs the model to omit unsupported values rather than invent them.
After projection, the initial draft contains dataset-level values such as identifiers, title, description, keywords, creators, and type.
The activity relation \texttt{was\_generated\_by} remains empty at this point.
It is populated by the subsequent provenance core construction step.

\subsection{Provenance Core Construction}
\label{sec:provenance_core_construction}

The provenance core step introduces the first activity structure into the draft.
Its purpose is to create a stable parent object for later provenance and attribute enrichment.
The step focuses on one generic \texttt{DataGeneratingActivity}.
This activity represents the analytical process that produced the dataset and is written to the \texttt{was\_generated\_by} field of the dataset artifact.

The step is implemented as a constrained \ac{LLM}-based intent-generation step followed by deterministic backend construction.
The model receives the current draft and an orientation context.
The dataset-level summary is available through the draft description.
The separate orientation context consists of the ranked file summaries.
It does not receive the full evidence context at this point.
The prompt asks the model to identify the core data-generating activity and to classify related objects by their provenance role.
The model does not modify the \ac{DCAT-AP+} artifact directly.
Instead, it returns structured intents in a fixed response schema, as shown in \cref{fig:prov-core-input-output}.
These intents describe a core data-generating activity, a realized plan, agents, evaluated targets, input entities, input activities, and output entities.
The backend then interprets the structured response.
It discards empty intents, removes duplicate role candidates, preserves the returned order for the remaining candidates, assigns generated local identifiers, and translates the resulting intents into profile objects and patch operations against the initialized draft.

\begin{figure}[H]
    \centering
    \includegraphics[width=1\textwidth]{figures/prov-core-input-output.png}
    \caption{Input and output schema for the provenance core construction step. The model receives the shallow profile draft and ranked file summaries as orientation context, and returns structured intents for the data-generating activity, its plan, agents, evaluated targets, inputs, and outputs.}
    \label{fig:prov-core-input-output}
\end{figure}

The core construction step is constrained by its scope.
At most one direct \texttt{DataGeneratingActivity} is created for the dataset artifact, and it is written to \texttt{was\_generated\_by}.
The \texttt{realized\_\allowbreak plan} relation is treated as a single object and is only populated when a suitable procedure- or instruction-like intent is available and the field has not already been set.
For the list-valued relations, the prompt does not assume a fixed number of agents, inputs, outputs, evaluated targets, or prior input activities.
Instead, the model may return multiple role-bearing intents.
The backend inserts only the role candidates that remain after the cleanup and normalization step described above.

These controls are workflow constraints for the initial core draft, not profile cardinalities.
The core step should identify the main production activity and the most relevant objects that have a clear provenance role in relation to that activity.
This follows the broader reliability concern that \ac{LLM}-based information extraction becomes less stable when prompts invite weakly constrained, context-dependent, or overly broad structured outputs \cite{xu2024generativeie,liu2024lostmiddle}.
In this workflow, reliability is addressed by separating model-generated construction intents from deterministic backend construction.
The model proposes role assignments, while the backend decides how these intents are inserted into the draft.
This reduces the risk that file inventories, low-level parameter records, or repeated textual variants are copied into the profile as separate activity objects.
It also supports more stable later attribute placement, because subsequent construction steps can attach attributes to an already established provenance structure.
Further details are handled later through parent-scoped attribute construction and requirement checks.

The placement rules follow the \ac{DCAT-AP+} design patterns described in \cref{sec:dcat-ap-plus-chemdcat-ap}, which act as construction guidance here \cite{dcatapplusDocumentation}.
The \texttt{realized\_\allowbreak plan} relation is used for the procedure or instruction set followed by the activity.
The \texttt{carried\_out\_\allowbreak by} relation is used for \texttt{Agentic\allowbreak Entity} objects that bear responsibility for or influence the activity.
The \texttt{had\_input\_\allowbreak entity} and \texttt{had\_input\_\allowbreak activity} relations are used for entities or prior activities used by the data generating activity.
The \texttt{had\_output\_\allowbreak entity} relation is used for entities generated by the activity.
The \texttt{evaluated\_\allowbreak entity} and \texttt{evaluated\_\allowbreak activity} relations are narrower input roles and mark the entity being measured or observed and the process being studied.
For example, a spectrum can be the output of an acquisition process or the target of an evaluation.
After all intents have been placed, the backend checks the draft for schema validity.
If schema validation fails or recommended fields are missing, the draft is marked as incomplete and undergoes an additional step, to populate the missing fields.
During that step a selection of evidence signals are collected from the evidence grounding set based on the specific shape where the information is missing.
Then, an \ac{LLM} is prompted to try and populate the missing fields with the selected evidence.
After completion, the resulting core draft provides the parent structure for later attribute construction and requirement checks.

\subsection{Parent-Scoped Attribute Construction}
\label{sec:parent_scoped_attribute_construction}

Parent-scoped attribute construction adds quantitative and qualitative attributes to the parent objects that already exist in the core draft.
The backend freezes the core draft as context and iterates over every parent object that has a non-empty title or description.
These parents include the data-generating activity, technical agents, evaluated entities, evaluated activities, input entities, input activities, and output entities.

For each parent, the workflow selects an evidence packet from the evidence grounding set.
The selection matches evidence candidates whose category and routing role are semantically local to the parent's position in the draft.
If no matching evidence is found, the parent is skipped.
This prevents the model from inventing attributes.
The \ac{LLM} then receives the core draft, the target path, the target class, the selected evidence notes, as well as sourounding context in form of evidence notes from nearby dataset locations, and a system instruction.
The instruction asks the model to decide which facts, if any, are useful profile-level attributes for this parent.
It explicitly instructs the model to exclude source-record metadata, provenance bookkeeping, file paths, and identifiers for other objects.
The model then only returns structured quantitative and qualitative attribute intents.

The backend owns the concrete schema path.
It transforms each accepted intent into an attribute object, assigns a generated local identifier, and validates each insertion against the target schema.
Weak or unsupported attribute intents are rejected at this stage.
This includes attributes with unclear intent, placeholder-like labels, generic values, or labels and values that are not supported by the selected parent-local evidence.
Duplicate attributes under the same parent are also rejected.
A parent attribute ledger records every accepted and rejected attribute, including the evidence identifiers that supported it and the reason for rejection when applicable.
This draft is the working document for semantic requirement evaluation.

\subsection{Semantic Requirement Evaluation}
\label{sec:semantic_requirement_evaluation}

Semantic requirement evaluation checks the attribute-enriched draft against a set of semantic adequacy requirements.
These requirements are distinct from the completeness criteria checked earlier, as they focus on the semantic quality of the placed values rather than their presence or absence.
Eight semantic requirements are defined.
They cover dataset title identity, dataset description scope, generation activity reality, technical agent kind, method plan presence, activity evaluation target, attribute range decomposition, and attribute parent placement.
The dataset description scope requirement reflects the earlier draft initialization step.
The description already comes from the dataset-level summary.
The semantic check therefore asks whether it remains a compact dataset-level summary and whether it repeats facts that are already represented by structured activity, agent, plan, target, or attribute fields.
The generation activity requirement checks whether the activity title, description, and type describe a real acquisition, measurement, processing, or generation activity.
Fields that do not meet this requirement and cannot be streamlined are flagged as unresolved.
The evaluation target requirement checks aboutness rather than simple presence.
It asks whether the evaluated entity or evaluated activity is the concrete object measured, observed, analysed, or studied.

Each semantic requirement declares target paths, evidence hints, and allowed evidence categories.
For each requirement, the workflow selects a small evidence packet and a context window from the evidence grounding set.
The workflow then runs a constrained \ac{LLM} evaluation for each semantic requirement.
The model receives a draft excerpt that contains only the values at the requirement's target paths, the selected evidence, and the context window.
For attribute parent placement, the excerpt is broader.
It contains the relevant parent objects and their quantitative and qualitative attributes, so the model can reason about placement in the compact draft context.
It returns one assessment per requirement with a status, a quality score, and a rationale.
After the \ac{LLM} returns its assessment, the backend applies guard checks.
These guards override the model's assessment when the draft state contradicts it.
For example, if the model marks a requirement as fulfilled but none of the target paths contain a placed value, the backend downgrades the status.
If the model omits a requirement entirely, the backend records it as unanswered.
The backend also performs guard checks for technical agents, evaluation targets, method plans, and collapsed range attributes.
These guards do not replace the semantic assessment.
They prevent fulfilled ratings when the draft state makes fulfillment impossible.

After all requirements have been evaluated, each requirement carries a status (fulfilled, partial, missing, or not applicable), a quality score, a rationale, and the evidence that was selected for it.
Requirements that are not fulfilled are candidates for semantic reconstruction.

\subsection{Semantic Reconstruction}
\label{sec:semantic_reconstruction}

Semantic reconstruction attempts to repair the defects identified by semantic requirement evaluation.
It does not search for new evidence.
It works only with the current draft, the evidence already selected for each requirement, and the context window from the evidence grounding set.
The reconstruction proceeds requirement by requirement in a fixed order.
Attribute range decomposition and attribute parent placement run before the higher-level provenance and dataset identity requirements.
The order is attribute range decomposition, attribute parent placement, technical agent kind, method plan presence, generation activity reality, dataset title identity, dataset description scope, and activity evaluation target.

For each requirement that is not already fulfilled, the workflow first checks whether a narrow deterministic repair is available.
This only applies to self-referential \texttt{evaluated\_\allowbreak activity} links where an activity references itself.
In that case, the backend compiles a remove action from the draft without calling the \ac{LLM}.
If the deterministic pass produces repair actions, they are applied immediately.

If the deterministic pass produces no actions, the workflow falls back to an \ac{LLM}-based diagnosis.
The model receives a draft excerpt at the requirement's target paths, the selected evidence, and the context window.
It returns a list of diagnosed defects.
Each defect specifies a defect type, a target path, entry indices for array entries, a recommended action (merge, remove, move, replace, or append), and whether a new value must be synthesized.
The backend then compiles these diagnoses into concrete write actions.
Mechanical actions (merge, remove, move) must not request synthesis.
If a diagnosis requests synthesis for a mechanical action, it is rejected.
For append or replace actions that need a new value, the workflow calls a separate synthesis step.
This step sends the diagnosed defect, the current value at the target path, and a small schema branch to the \ac{LLM}.
The model returns only the replacement value, not a profile patch.
The backend validates that the synthesized value matches the target schema.
Array replacements must identify exactly one entry; collection-wide replacements are rejected.
For range decomposition, the diagnosis must identify the collapsed range entry and the required bound attributes.
The \ac{LLM} may request synthesis for separate minimum and maximum attributes.
The backend then writes those attributes as schema-valid append actions and removes the collapsed range entry.
For evaluation-target requirements, relation synthesis is refused because evaluated targets require explicit projection evidence.

All compiled write actions are applied one at a time.
Each action is validated against the full profile schema before it is committed.
If an action produces an invalid draft, it is rejected and the draft is left unchanged.
If a whole reconstruction attempt fails validation, it is rolled back to the state before the attempt.
Valid actions are applied even if other actions from the same diagnosis are rejected.
This allows the workflow to salvage independently valid repairs.

After reconstruction, the workflow re-evaluates the semantic requirements against the reconstructed draft.
This produces the final semantic requirement scores.
Requirements that remain unfulfilled after reconstruction are recorded with their status and rationale.
The workflow then assembles a requirement report that combines three scores: a coverage score that counts filled profile fields, a semantic requirements score that weights each requirement by its quality and declared weight, and a source trace score that measures how much of the placed draft content is supported by evidence from the source files.
The report distinguishes requirements that were patched, requirements that were reconstructed, and requirements that remain unresolved.
This report is the basis for the manual curation step that follows.

\section{Manual Curation}
\label{sec:manual_curation}

Manual curation provides a human validation checkpoint between automated artifact construction and vocabulary mapping.
Although the preceding stages enforce schema validity, evaluate evidence support, and attempt to repair semantic defects, they cannot guarantee that every generated description reflects the scientific meaning and overall context of the dataset.
In particular, an \ac{LLM} may produce a locally plausible interpretation that is too broad, too specific, or inconsistent with the intended role of an object.
The manual curation stage therefore allows a domain-informed user to review and refine the reconstructed draft before semantic identifiers are added.

The curation interface is organized around the nested structure of the \ac{DCAT-AP+} artifact.
As shown in \cref{fig:manual-curation-interface}, the tree view on the left represents the objects and relations contained in the draft and serves as the primary navigation mechanism.
Selecting an object opens its current content in an editable form on the right.
This allows the user to inspect the object in its structural context while directly modifying its textual fields, such as titles and descriptions.

    \centering
    \includegraphics[width=0.8\textwidth]{figures/manual-curation-interface.png}
    \caption{Manual curation interface with tree-based navigation of the \ac{DCAT-AP+} draft and editable object fields.}
    \label{fig:manual-curation-interface}

Individual fields can additionally be protected against later automated modification.
A protected field retains the curator-approved value during subsequent workflow stages.
This provides an explicit distinction between values that remain provisional and values that have been reviewed and accepted by the user.

The current prototype supports content-level curation of objects that are already present in the draft.
It does not yet support structural editing.
Users cannot create additional profile shapes or move existing shapes to different parent objects.
Consequently, the curation stage can correct or clarify the contents of the generated structure, but structural omissions or incorrect parent assignments that were not resolved during semantic reconstruction cannot yet be repaired through the interface.

\section{Vocabulary Mapping}
\label{sec:vocabulary_mapping}

Vocabulary mapping is performed after the schema-valid \ac{DCAT-AP+} draft has been reconstructed and curated.
The stage follows the classifier mixin pattern discussed in \cref{sec:dcat-ap-plus-chemdcat-ap}.
In \ac{DCAT-AP+}, this pattern provides the classification slots \texttt{type} and \texttt{rdf\_type} for the central profile shapes, as well as \texttt{unit} and \texttt{has\_quantity\_kind} for quantitative attributes \cite{dcatapplusDocumentation}.
These slots carry different semantic commitments.
The \texttt{type} slot maps to \texttt{dcterms:type} and supports controlled-vocabulary categorization.
The \texttt{rdf\_type} slot maps to \texttt{rdf:type} and supports links to classes from formal ontologies.
These two slots can be applied to activities, entities, agents, plans, surroundings, and qualitative or quantitative attributes.
Quantitative attributes also have the \texttt{unit} and \texttt{has\_quantity\_kind} slots, which support links to \ac{QUDT} terms.
This workflow populates the \texttt{dcterms:type} slot with terms from \ac{Voc4Cat} and \ac{nmrCV}, which are structured taxonomies and not formal ontologies in the strict sense.
The \texttt{rdf\_type} slot is not populated in this workflow.

In this stage, the program first identifies draft elements that are eligible for vocabulary mapping.
An activity, entity, agent, plan, surrounding, or attribute is considered eligible when it contains a non-empty \texttt{title} or \texttt{description}.
For each eligible element, the available text is collected into a self-contained bundle.
Those bundles consist of the element's title and description, as well as a the target path in the schema in a compressed form, e.g. \texttt{dataset.was\_generated\_by.carried\_out\_by} with the parent elements' titles and descriptions as surrounding context.
This bundle is then passed to an \ac{LLM}, which generates two complementary retrieval queries and chooses vocabularies that these queries are run against.
For the prototype in this work, the \ac{LLM} could choose \ac{Voc4Cat}, \ac{nmrCV} or both.
The vector query paraphrases the underlying concept in natural language, whereas the full-text query preserves concise domain terms, labels, abbreviations, or parameter codes that may occur literally in vocabulary entries.
% \Cref{fig:query-generation} shows an example input and output for the query generation step.

% Here must be a figure showing the input and output for the query generation step. This also includes the payloads

The two queries are executed separately against the vocabulary store.
The vocabulary store is implemented as a property graph store with vector indexing and full-text indexing, as further described in \cref{sec:neo4j_graph_store}.
Vector retrieval ranks terms by the semantic similarity of their embedded labels and definitions, whereas full-text retrieval ranks terms by lexical overlap with indexed literal properties.
The result lists are combined using reciprocal-rank fusion and enriched with a bounded amount of graph context around the retrieved terms.
This produces a compact candidate set for the subsequent selection step.

The \ac{LLM} receives the original bundle, both queries, the retrieved candidates, and their local graph context.
It must either select one candidate URI from the supplied set or abstain.
When no candidate denotes the same concept as the draft element, the original value is retained and the grounding warning remains visible in the final artifact.


\section{Infrastructure and Implementation}
\label{sec:infrastructure_and_implementation}

The prototype is implemented as a service-oriented application composed of four main services.
The workflow \ac{API}, the user interface, a Neo4j property graph database, and an Ollama model server.
The services are packaged as separate containers and coordinated through Docker Compose.
This separation isolates the workflow logic, user interaction, vocabulary storage, and model execution while allowing the individual services to be deployed according to their hardware requirements.

The services can run together on one workstation or server.
Alternatively, the \ac{API} can connect to Neo4j or Ollama instances hosted on another machine.
This is particularly relevant for Ollama because local inference may require a server equipped with sufficient system memory or a supported \ac{GPU}.
The browser-based interface communicates with the workflow through \ac{HTTP}, so users do not need direct access to the Python runtime, the database, or the model server.
In the containerized deployment, the frontend also acts as the public entry point and forwards \ac{API} requests to the backend service.

\subsection{Workflow Runner}
\label{sec:workflow_runner}

The workflow backend is primarily implemented in Python as a FastAPI application \cite{ramirezFastAPI}.
FastAPI exposes the workflow functionality through an \ac{HTTP} interface and generates an interactive description of the available endpoints.
The exposed operations cover dataset ingestion, preprocessing, extraction execution, profile management, semantic vocabulary operations, configuration, progress monitoring, and result retrieval.
Long-running operations are registered as asynchronous tasks so that an extraction run can continue after the initial request has returned.
The user interface can subsequently query the current workflow state and retrieve intermediate or final artifacts.

The backend follows a layered organization.
The \ac{API} layer defines the externally available endpoints and validates incoming and outgoing payloads.
The service layer coordinates complete application operations, such as dataset preparation, evidence extraction, profile construction, vocabulary grounding, and result persistence.
The domain layer contains the workflow-specific logic.
This includes the prompts used for model interactions, deterministic heuristics, validation rules, evidence-routing procedures, schema projections, requirement checks, and vocabulary-query construction.

The FastAPI application also manages the lifecycle of the external services used by the workflow.
During startup, it establishes the Neo4j connection, initiates the configured model and vocabulary setup tasks, and prepares the shared application services.
During shutdown, remaining background tasks are cancelled and the Neo4j and Ollama client connections are closed.

\subsection{Ollama Model Server}
\label{sec:ollama_model_server}

Ollama provides the local model-serving infrastructure.
It exposes an \ac{HTTP} interface through which the workflow sends \texttt{generate} and \texttt{embedding} requests.
The generation model performs the language-based extraction, classification, evaluation, reconstruction, query-generation, and candidate-selection tasks described in the preceding sections.
The generation models used in this work are gemma3:4b, gemma3:12b, and gemma3:27b \cite{gemma3technicalreport}.
These models are all 


A separate embedding model creates vector representations for semantic chunking and vocabulary retrieval.
The model configuration can be defined through the application configuration or adjusted for subsequent requests through the user interface.
The selectable runtime options include the chat model, embedding model, maximum context length, embedding batch size, generation temperature, output-token restriction, and the use of the \ac{GPU} for embedding requests.
Models can also be downloaded to or removed from the configured Ollama host through the interface.
This makes it possible to adapt the workflow to the memory capacity and model availability of the deployment machine without changing the workflow implementation.

Container-level Ollama settings are supplied as environment variables.
For the prototype, these include the quantization type of the key--value cache, model-retention behavior, Flash Attention, network binding, and memory-mapping behavior.
The configuration

\begin{verbatim}
OLLAMA_KV_CACHE_TYPE=q8_0
OLLAMA_KEEP_ALIVE=-1
OLLAMA_FLASH_ATTENTION=1
OLLAMA_NO_MMAP=0
\end{verbatim}

uses a quantized key--value cache and keeps loaded models resident rather than unloading them after individual requests.
Flash Attention is enabled when supported, while memory mapping remains available.
These parameters affect the memory consumption and loading behavior of the model server rather than the semantic behavior of the workflow.
An additional Docker Compose configuration can reserve available NVIDIA devices for the Ollama container.
Consequently, the same workflow can be operated with CPU inference, local GPU acceleration, or a remote Ollama instance on a dedicated inference server.

\subsection{Neo4j Graph Store}
\label{sec:neo4j_graph_store}

Neo4j serves as the semantic vocabulary store.
It was selected because its property graph model supports both graph traversal and indexed retrieval over the same vocabulary resources.
The database stores the imported vocabulary terms, their literal properties, their relationships, generated embeddings, and information about the vocabulary from which each resource originates.
The APOC extension is enabled for additional graph-processing operations.

The database is initialized through a vocabulary-bootstrap procedure.
During this procedure, the configured RDF vocabularies are retrieved from their source locations or supplied as uploaded RDF files.
They are parsed into RDFLib graphs and normalized before their transfer to Neo4j.
The current preprocessing includes deterministic replacement of blank nodes with generated identifiers and filtering of literals that are explicitly marked with unsupported languages.
The normalized RDF statements are then converted into the property graph representation according to the mapping rules described below.

Each imported vocabulary is represented by a vocabulary-scheme node connected to its imported resources.
After import, the backend examines the RDF types, literal properties, and relationships available for the vocabulary terms.
It then creates full-text and vector indexes for the relevant term types.
The full-text indexes cover textual properties such as labels, descriptions, synonyms, or symbols.
For vector retrieval, the backend constructs a textual representation of each resource, sends it to the Ollama embedding model, and stores the resulting vector on the corresponding graph node.

The bootstrap is designed to preserve an existing graph.
If a configured vocabulary has already been imported, its resources are not inserted a second time.
Missing or outdated embeddings can nevertheless be generated after startup.
The graph store is therefore prepared once and can subsequently be reused by multiple extraction runs without rebuilding the vocabularies for every dataset.

During vocabulary mapping, the \ac{API} submits the vector and full-text queries to Neo4j independently.
The database returns indexed candidates and provides bounded graph traversal around the retrieved seed terms.
The graph store is thus not used to persist the reconstructed \ac{DCAT-AP+} artifact itself.
Its primary role in the prototype is to provide the indexed and connected semantic resources required for vocabulary grounding.

\subsection{User Interface}
\label{sec:user_interface}

The user-facing application is implemented as a React and TypeScript frontend built with Vite.
For the containerized deployment, the compiled application is served by Nginx.
Nginx also forwards requests under the configured \ac{API} path to the FastAPI service.
As a result, the browser communicates with one public application endpoint, while the remaining services can remain accessible only within the host or container network.

The interface covers the complete interaction cycle of the prototype.
It allows users to upload dataset packages, select preprocessing and chunking options, start extraction workflows, and inspect their current progress.
Intermediate workflow products can be reviewed to make the behavior of the extraction process visible.
The interface also exposes configuration options for the selected models and their runtime parameters.

After automated profile construction, the same interface provides the manual curation view described in \cref{sec:manual_curation}.
The tree representation is used to navigate the nested artifact, while editable controls show the content of the selected object.
Curated fields can be protected against subsequent automated modification.
After vocabulary grounding has completed, the resulting metadata artifact and its associated workflow reports can be retrieved and exported through the interface.

The frontend does not implement the extraction or semantic-mapping rules itself.
It acts as a presentation and control layer over the backend \ac{API}.
This keeps workflow decisions in the Python domain layer and prevents the browser implementation from becoming a second, potentially inconsistent implementation of the extraction process.
