\label{chap:results_and_evaluations}

The implemented prototype is evaluated as an end-to-end application for \ac{LLM}-assisted semantic metadata extraction from heterogeneous dataset packages.
The system is not limited to isolated prompt experiments.
Instead, it implements an executable workflow that connects dataset ingestion and preprocessing with evidence-backed metadata construction, semantic review, and vocabulary grounding.
The primary evaluation focus is the automatically generated metadata draft without manual curation as a case study baseline.
It is examined how far a domain-agnostic \ac{DCAT-AP+} profile can carry the extraction of curator-relevant metadata before domain-specific profile extensions are introduced.
The evaluation therefore distinguishes structural validity from semantic and scientific correctness.
Structural validity can be checked automatically, because the generated artifacts are validated against the \ac{JSON} schema derived from the same \ac{LinkML} profile that also underlies the \ac{DCAT-AP+} shape representation.
This ensures that the generated draft follows the expected object structure, required fields, datatypes, and nesting constraints.
However, structural validity does not imply that every extracted value is faithful to the source package, placed under the most appropriate profile element, or scientifically meaningful in the context of the measurement.
These aspects are harder to evaluate automatically, because they require interpretation of the source data, the intended metadata model, and the domain-specific role of individual values.

For this reason, the chapter does not assign global quality scores to extraction runs.
A metric-based evaluation would require a sufficiently large and curated reference corpus of \ac{DCAT-AP+} metadata records.
Such a corpus was not available for the investigated \ac{NMR} data.
Moreover, the same source package can often be represented by more than one defensible metadata structure, especially when generic provenance and attribute patterns are used.
A small reference set would therefore risk measuring agreement with one modelling style rather than the general correctness of the extraction.
Instead, this chapter uses a diagnostic case-study evaluation.
It traces selected curator-relevant facts through the workflow and inspects whether they are preserved, transformed, misplaced, or omitted in the generated draft.

\section{Workflow Evaluation Setup}
\label{sec:evaluation-setup}

The case study uses the two \textsuperscript{1}H \ac{NMR} package variants introduced in \cref{sec:dataset}.
Both packages originate from the same underlying measurement, but expose different metadata affordances.
The raw Bruker archive is closer to the instrument output and contains vendor-specific acquisition and processing files.
The ChemSpectra-derived export is closer to a repository-facing package and contains derived resources such as a \ac{JCAMP-DX} spectrum, a rendered spectrum image, and a textual dataset description.
The comparison therefore does not evaluate different scientific measurements, but how different representations of the same measurement affect source accessibility, evidence traceability, provenance representation, and profile construction.

The case study follows a small set of curator-relevant facts through the workflow.
This traced fact set is not a formal metadata standard.
It is a scoped inspection aid for asking whether basic facts about the measurement remain visible when the workflow transforms the source package information into a profile-valid draft, whether they are moved to unsuitable places, or whether they disappear.
For the present measurement, the traced facts are the dataset identity as \textsuperscript{1}H \ac{NMR} data, the observed nucleus, solvent information, pulse sequence, instrument type, observed resonance frequency, and the distinction between raw and derived package resources.
The observed frequency is treated as a specific acquisition value of the \textsuperscript{1}H channel, recorded in the source files as approximately 500.13~MHz, rather than only as the nominal 500~MHz instrument description.
These facts were selected because they provide basic acquisition and package-context information that supports manual review of an \ac{NMR} dataset \cite{Schober2018nmrML}.

In the raw dataset, the dataset identity is available through Bruker acquisition and processing files and through the human-readable title file \texttt{10/pdata/1/title}.
The observed nucleus is explicitly recorded in \texttt{10/acqus} and \texttt{10/acqu} as \texttt{NUC1=<1H>}.
The same acquisition context records the solvent as \texttt{SOLVENT=<CDCl3>} and the pulse sequence as \texttt{PULPROG=<zg30>}.
The observed resonance frequency appears in the \texttt{SFO1} parameter as 500.133088507478.
Instrument information is available in \texttt{10/uxnmr.info}.
This file identifies an Avance III NMR spectrometer and reports a rounded \textsuperscript{1}H frequency of 500.13~MHz.
The raw package also contains the binary \texttt{fid} signal, acquisition files, processing files, shim values, audit trail, pulse program, and instrument configuration.
In the ChemSpectra export, the dataset is identified in \texttt{dataset\_description.txt} as a \textsuperscript{1}H NMR dataset.
The \texttt{10.edit.jdx} file records the observed nucleus, the \texttt{CDCl3} solvent, the \texttt{zg30} pulse sequence, and the observed frequency of 500.133088507478.
The instrument type is available in the textual dataset description as \texttt{Bruker Avance 500 MHz}.
Compared with the raw dataset, the relevant metadata in this package is concentrated in the \ac{JCAMP-DX} spectrum file and the textual dataset description.

\section{Preprocessing}
\label{sec:results-preprocessing}

Preprocessing is the first stage of the workflow.
It converts the uploaded package into file-level and text-level representations that can be inspected by later stages.
At this point, the system is not expected to understand the scientific meaning of the dataset.
The relevant question is whether the information needed for later metadata construction remains available after conversion.
For the present case study, this mainly concerns compact \textsuperscript{1}H \ac{NMR} acquisition facts such as observed nucleus, observed frequency, solvent, pulse program, and instrument context.

The evaluated runs use the preprocessing settings described in \cref{sec:preprocessing}.
These settings are relevant for the present \textsuperscript{1}H \ac{NMR} packages because many metadata facts are not written as prose.
They appear as compact parameter records in vendor files.
A typical example is the observed-frequency line \texttt{SFO1= 500.133088507478}.
The text-quality gate is therefore expected to avoid discarding such lines merely because they contain many digits or have little natural-language structure.

For the example line, the key--value syntax provides a strong positive signal.
The short alphabetic token \texttt{SFO} also counts as a readable token.
The high digit ratio is penalized, but this penalty does not outweigh the structured-text signal.
As shown in \cref{tab:text-quality-gate-example}, the resulting score remains above the configured keep threshold.
The line therefore remains available for later workflow stages.

This example shows that the preprocessing configuration can preserve compact acquisition parameters in the inspected \textsuperscript{1}H \ac{NMR} packages.
The result should not be read as a general validation of the gate for all vendor formats.
The thresholds are tunable, and the present evaluation only inspects whether the selected case retains the source lines needed for the later metadata trace.

After text filtering, the retained text is divided into chunks.
Chunking is the step that creates the text passages inspected by the later extraction prompts.
It does not interpret the facts yet.
The relevant question is whether selected source facts remain visible in the chunks and whether related facts stay close enough to be interpreted together.
The baseline run uses fixed-token chunking with a target and maximum size of 1024 tokens.
This simple strategy keeps the passages within a size range suitable for the local \ac{LLM} models used in this work.

With this configuration, the raw Bruker package is represented by 32 textual chunks from 15 source files.
The ChemSpectra export is represented by 33 textual chunks from three textual sources.
The raw binary \texttt{fid} file and the rendered ChemSpectra image remain package resources, but they do not contribute substantive text content to the chunk set.
\Cref{fig:chunking-inspection-raw-bruker} illustrates the inspection view for the raw Bruker package.
The view keeps the file origin of each chunk visible and reports how many retained text lines are included per source file.
This supports the qualitative inspection of both fact preservation and fact separation.

The selected facts are not lost during chunking.
In the raw package, acquisition-file chunks preserve lines such as \texttt{NUC1= <1H>}, \texttt{PULPROG= <zg30>}, \texttt{SFO1= 500.133088507478}, and \texttt{SOLVENT= <CDCl3>}.
Another chunk preserves the broader instrument context, including the \texttt{Avance III NMR spectrometer} and the rounded \textsuperscript{1}H frequency of 500.13~MHz.
In the ChemSpectra export, the first \ac{JCAMP-DX} header chunk keeps observed frequency, observed nucleus, solvent, reference information, and pulse sequence together.

The main limitation of the baseline chunking is therefore not direct fact loss, but fact separation.
For NMR metadata, acquisition settings, sample information, instrument context, and spectral data belong to the same experimental description \cite{Schober2018nmrML}.
This matters because later extraction prompts can only use the context that is visible in the inspected passage.
In the raw Bruker package, observed nucleus and pulse-program information can appear in neighbouring chunks rather than in the same chunk as solvent and observed frequency.
The ChemSpectra export is more compact in this respect, because several relevant header fields are co-located in the same \ac{JCAMP-DX} chunk.

Overall, preprocessing and chunking fulfil their preservation task for the inspected packages.
The selected reference facts remain available for later workflow stages.
However, fixed-token chunking does not guarantee that all related NMR facts are presented together.
This makes the raw Bruker package more dependent on later evidence aggregation across neighbouring chunks, while the ChemSpectra export provides a more compact header representation for several acquisition-level facts.

\section{Dataset Overview}
\label{sec:evaluation-overview-observations}

The dataset overview is meant to give the workflow a quick map of the package.
It should answer simple questions such as which files look important, which files look like raw data, and where detailed metadata is likely to be found.
It is not supposed to be the final evidence for the followed facts.

The dataset overview stage was inspected as orientation output before evidence collection.
It is not treated as source evidence for the reference facts.
Instead, it is evaluated according to whether it points later extraction steps toward files that are likely to contain relevant information.
This distinction matters because the overview works at file and package level, while the reference facts often occur as compact parameter records inside individual files.

For the raw dataset, the baseline overview gives source-location guidance.
The two direct acquisition files are ranked first and second.
Both are summarized as files that contain \enquote{parameter settings for a Bruker NMR experiment} and that configure the instrument and experimental conditions.
This correctly identifies the acquisition files as important locations for later evidence extraction.
However, the summary remains generic.
It does not expose the concrete values \texttt{NUC1=<1H>}, \texttt{SOLVENT=<CDCl3>}, \texttt{PULPROG=<zg30>}, or \texttt{SFO1=500.133088507478}.

Other raw files are also described at file-role level.
The pulse-program file is described as a \enquote{Bruker NMR pulse program}, which points to the pulse-sequence evidence location, but the overview does not preserve the concrete \texttt{zg30} value.
The instrument-configuration file is summarized as containing \enquote{configuration information for a Bruker Avance III NMR spectrometer}, which correctly identifies an instrument-context source.
The rounded \textsuperscript{1}H frequency value is still not surfaced by the overview.
The binary signal file is described as raw \ac{NMR} data in a likely proprietary format with empty sampled content.
This supports the distinction between raw data and textual metadata, but it does not add acquisition values.
The overview also assigns broad acquisition, processing, and instrument-setting roles to several parameter files, so the resulting orientation is not sharply separated by scientific metadata role.

For the ChemSpectra export, the overview identifies the textual description as a dataset description containing instrument information and a file list.
It also identifies the \ac{JCAMP-DX} file as a \textsuperscript{1}H \ac{NMR} spectrum with spectral parameters, XY data points, and an automatically generated peak table.
This is the most important location hint for later extraction because the selected acquisition facts are concentrated in that spectrum file.
Nevertheless, the overview does not preserve the exact observed nucleus, the \texttt{CDCl3} solvent, the \texttt{zg30} pulse sequence, or the observed frequency as separate facts.

Overall, this behaviour follows the prompt contract of the overview stage.
The file-summary prompt asks for compact orientation and explicitly avoids separate metadata, setting, provenance, or numeric signal lists.
The overview prompt also states that its output is guidance only and not evidence for later extraction calls.
The evaluation therefore checks whether the overview points to likely source locations and whether its summaries misdirect later stages.
The selected acquisition facts still have to be checked in chunk-level evidence, where the workflow has access to the relevant source lines rather than only file summaries.

Step assessment: The overview is partly successful.
It points to the right files and gives a useful first orientation, especially for acquisition files and the \ac{JCAMP-DX} spectrum file.
However, it stays too general to preserve the exact values being traced, so it cannot be used as proof that those facts survived.

\section{Evidence Collection}
\label{sec:evaluation-evidence-collection-observations}

Evidence collection is where the workflow starts looking inside the chunks for statements that might become metadata.
In simple terms, this stage should pick out useful source snippets and attach rough labels so later stages know whether a snippet looks like a resource, instrument, measurement, method, or other kind of signal.

The inspection basis for the next stage is the raw dataset evidence-note output of the baseline configuration.
The evidence categories are workflow-routing labels rather than domain concepts.
They separate resource, instrument, measurement, method, software, activity, surrounding-context, and residual metadata signals for later profile construction.
Across 32 chunks from 15 textual source files, this output contains 120 portable notes, 59 contextual notes, and 9 rejected candidate notes.
\Cref{fig:evidence-category-distribution-raw-baseline} shows the category distribution for these three evidence groups.
The horizontal axis lists the evidence categories, while the vertical axis gives the number of evidence notes.
Blue bars represent portable notes, green bars represent contextual notes, and red bars represent rejected candidate notes.

The portable notes are concentrated in the categories \texttt{resource\_\allowbreak{}signal}, \texttt{instrument\_\allowbreak{}signal}, and \texttt{measurement\_\allowbreak{}signal}.
These three categories are nearly balanced, with 34 resource signals, 33 instrument signals, and 32 measurement signals.
The contextual notes are dominated by \texttt{measurement\_\allowbreak{}signal}, which accounts for 41 of the 59 contextual notes.
Rejected candidates are comparatively rare and occur mainly in \texttt{resource\_\allowbreak{}signal}.
The most frequent portable roles are \texttt{parameter} and \texttt{descriptor}, followed by smaller numbers of \texttt{qualitative\_\allowbreak{}attribute}, \texttt{identity}, and \texttt{context} roles.
The stage therefore produces a broad signal inventory, but the inventory is still organized through coarse workflow categories rather than domain-specific \ac{NMR} concepts.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=\textwidth]{figures/evidence_category_distribution_raw_baseline.png}
    \caption{Distribution of evidence categories in the raw dataset baseline run.}
    \label{fig:evidence-category-distribution-raw-baseline}
\end{figure}

Several reference facts are detected at chunk level.
The pulse sequence is detected directly from \texttt{10/acqu} as the claim that the \ac{NMR} experiment uses the \texttt{zg30} pulse program, with \texttt{PULPROG=<zg30>} as evidence text.
This note is classified as \texttt{resource\_\allowbreak{}signal} with the role \texttt{descriptor}.
Within the available category set, \texttt{method\_\allowbreak{}signal} would have been the closer routing category, while a domain-specific label such as pulse sequence would have expressed the curator-facing role more directly.
The solvent is detected directly from \texttt{10/acqus} as the claim that the solvent is \texttt{CDCl3}.
This note is classified as \texttt{instrument\_\allowbreak{}signal} with the role \texttt{parameter}.
The \texttt{parameter} role is partly plausible because the solvent appears as an acquisition parameter, but \texttt{instrument\_\allowbreak{}signal} does not express the curator-facing role of \texttt{CDCl3} as solvent or reference context.
Within the current category set, \texttt{measurement\_\allowbreak{}condition} would have been closer, although a domain-specific solvent or reference label would be more precise.
The instrument description is detected from \texttt{10/uxnmr.info} as the claim that the spectrometer is an \texttt{Avance III NMR spectrometer}.
This note is classified as \texttt{instrument\_\allowbreak{}signal} with the role \texttt{identity}.
This classification is appropriate because the source line identifies the spectrometer type, so \texttt{instrument\_\allowbreak{}signal} with the role \texttt{identity} matches the curator-facing interpretation.
The same source context also contains the rounded \textsuperscript{1}H frequency value of 500.13~MHz, but this value is not represented as a separate claim in that note.
The observed-nucleus value \texttt{NUC1=<1H>} is detected as a direct candidate note, but it is removed by deterministic lexical deduplication over short structured parameter lines.
It is merged into a retained \texttt{PULPROG=<zg30>} note, even though the two source facts are not semantically equivalent.
The observed loss of \texttt{NUC1=<1H>} indicates that lexical deduplication is too permissive for compact structured parameter records.
In this case, unrelated \texttt{key=value} facts are grouped because they share short syntactic patterns, although they describe different acquisition properties.
These observations show that chunk-level evidence collection can recover source-level acquisition and instrument facts that the overview only indicated at file level, but the assigned workflow categories vary in how well they express the curator-facing role of each fact.

Step assessment: Evidence collection is partly successful.
Several selected facts are still detected before profile construction, so the workflow has not lost them completely.
However, the coarse category set does not always express the domain role that a curator would assign to the same source line, echoing ontology work in catalysis where reaction roles and catalyst relations require explicit semantic modelling \cite{behr2024reac4cat}.
This suggests two development directions for ongoing work.
Domain terms may need to be available already during evidence extraction, instead of being introduced only in downstream stages, as \ac{LLM}-based catalysis text mining also relies on domain knowledge injection and user-specified extraction schemas \cite{walls2025catminer}.
Alternatively, the category harness could be loosened so that the model can emit labels closer to the source signal, such as solvent, observed nucleus, pulse sequence, or observed frequency, following extraction designs that separate open extraction from later schema definition and canonicalization \cite{zhang2024edc}.
That direction would require more explicit downstream routing logic, because later stages could no longer rely only on the current fixed category set.
Another development direction is a model trained specifically for metadata-signal detection, as chemical text-mining work has shown for tasks including NMR data extraction \cite{zhang2024chemicaltextmining}.
Such a component could include \ac{NER}-style recognition of domain terms and parameter-value pairs, following chemistry-aware extraction pipelines for entities, properties, measurements, and relationships \cite{swain2016chemdataextractor}.


\section{Provenance Core Construction}
\label{sec:evaluation-core-construction-observations}

The provenance core is the first attempt to turn the collected orientation into a draft metadata structure.
In plain terms, it decides the basic story of the package: what activity happened, which data went in, which data came out, and which instruments or software were involved.
Detailed values are added later, but this skeleton matters because later details usually have to attach to it.

After evidence collection, the workflow leaves pure signal detection and enters the schema-aware construction of the metadata draft.
The first step in this construction phase is the provenance core, which defines the main activity, agents, input and output entities, and plans before detailed attributes are added.
This stage does not receive the evidence notes inspected above as direct input.
It is constructed from the dataset overview artifacts and the current dataset-level draft.
The inspection therefore evaluates whether the overview representation is sufficient to create the main activity skeleton.
In the baseline configuration with fixed 1024-token chunks and the gemma3:12b model, the raw dataset core is framed as \enquote{NMR Experiment Data}.
The generated dataset-level description is depicted in \cref{fig:evaluation-raw-core-description}.

The description is already semi-structured by the prompt and repeatedly foregrounds files, formats, parameter resources, shim values, and audit information.
It therefore gives the core step a provenance-oriented package frame, but it still does not surface the selected acquisition values as separate facts.
Following this frame, the provenance-core construction stage generates one activity titled \enquote{NMR Data Acquisition and Processing}.
The activity describes automated instrument control and data acquisition using Bruker TopSpin software.
It places \texttt{Bruker TopSpin} as technical agent, parameter files and shim values as inputs, audit trail generation as a preceding activity, and \texttt{NMR Experiment Data (FID)} as output.
The result is an acquisition-oriented provenance skeleton that preserves the raw signal as a central data output.

The ChemSpectra export is framed through the derived spectrum instead.
Its provenance core is titled \enquote{1H NMR Spectral Data of Chemical Compounds} and centers one activity titled \enquote{1H NMR Spectral Data Generation}, with processed \textsuperscript{1}H \ac{NMR} spectra in \ac{JCAMP-DX} and JSON formats as output.
The preceding raw measurement is not lost completely, because the draft contains an input activity titled \enquote{Signal Acquisition}.
However, this preceding activity remains generic and does not carry the exact acquisition-level facts.
The baseline contrast is therefore narrow but important.
The raw package is interpreted through acquisition and raw signal output, while the ChemSpectra export is interpreted through derived spectral data with only a generic preceding acquisition step.

Additional runs are considered as comparisons outside the baseline evaluation.
They show that provenance-core framing can vary across run configurations.
These comparisons indicate variation across configurations, but they are not designed to isolate the individual effects of model size or chunking method.
A separate comparison between the gemma3:4b model and a gemma3:27b model on the raw dataset shows different core specificity.
The gemma3:4b model produces a generic \enquote{NMR} and \enquote{data processing} frame, while the gemma3:27b model produces a more specific \enquote{Bruker Avance III NMR Spectral Data} and \enquote{NMR Data Generation} frame.

These results also show that the preceding overview stage can affect how the profile draft is structured.
Although it is designed as orientation rather than evidence, it can set the interpretive direction for the provenance core because the core prompt is constrained to the supplied overview context.
When this direction is incomplete or misleading, the core may propagate the misframing into the draft structure.
Further development should therefore focus on the handoff between dataset overview and provenance-core construction.
The observation suggests that intermediate summaries should not be completely decoupled from the downstream schema task.
Related extraction systems use user-specified schemas, domain knowledge injection, iterative prompting, or recursive schema interrogation to keep model outputs aligned with the target structure \cite{walls2025catminer,caufield2024spires}.
For this workflow, the overview should remain compact, but separate schema-oriented summary views may be needed for candidate activities, data products, agents, and plans before provenance-core construction.

Step assessment: Provenance core construction is partly successful.
It creates a readable skeleton and distinguishes the raw package from the derived ChemSpectra export, but it does not preserve the traced acquisition facts as explicit fields.
Because the core can vary with model and overview framing, mistakes at this point can shape the rest of the draft.

\section{Profile Refinement and Semantic Evaluation}
\label{sec:evaluation-profile-refinement-observations}

Profile refinement tries to fill the skeleton with more concrete details.
In simple terms, it asks where a source-backed detail belongs: for example, whether a pulse-program value should describe an input file, an activity, an instrument, or some other part of the draft.
The semantic evaluation then checks whether the enriched draft looks structurally reasonable.

This subsection combines the stages that add attributes to the provenance core and evaluate the resulting draft against semantic requirements.
At this point, evidence notes re-enter the workflow mainly through parent-scoped attribute construction, where the evidence notes are used to add attribute values to the provenance-core entities.
Semantic requirement evaluation then checks the resulting draft for profile-level requirements such as schema validity, trace support, activity targets, description scope, and attribute placement.

For the raw dataset, inspected runs show that attribute quality depends strongly on the available parent shape.
The strongest placement occurs in the gemma3:27b comparison run, where a dedicated \enquote{Pulse Program} as input entity of the data generating activity receives the attributes \enquote{Pulse Program Name} with the value \enquote{zg30}, \enquote{Flip Angle} with the value \enquote{30.0}, and a \enquote{ph31 Setting} with the value \enquote{0 2 2 0 1 3 3 1}.
These attributes are semantically plausible because \texttt{zg30} denotes a one-dimensional Bruker pulse program with nominal 30 degree excitation, while \texttt{ph31} records a pulse-program phase table, where each integer represents a specific phase value and the order of integers indicates the sequence of phases \cite{kim2019optimization}.
The relevant parent structure is shown in \cref{fig:evaluation-pulse-program-parent-shape}.
The important point is that \enquote{Pulse Program} is already represented as an input entity of the data-generating activity and can therefore receive pulse-program-specific attributes.

Here the input-entity parent already matches the source signal, so the attributes can be placed in a curator-readable structure.
Less suitable parent shapes lead to weaker attributes.

In the gemma3:4b comparison run, \texttt{TOPSPIN Version 3.2} appears to be reused as \enquote{pulse sequence length} under a \enquote{pulse program} parent.
These examples show that attribute construction can attach source-backed details, but the selected attributes and their placement vary across runs.
Single-run attributes are therefore diagnostic examples, not stable performance evidence.
The attribute enriched drafts still do not consistently place \texttt{CDCl3}, \texttt{NUC1=<1H>}, or \texttt{SFO1=500.133088507478} as explicit curator-facing acquisition facts.

For the ChemSpectra export, refinement draws strongly on the \ac{JCAMP-DX} spectrum and peak-table region.
It adds a number-of-points attribute to the XY data points and adds data-type, data-class, and peak-table-category attributes to the signal-acquisition activity.
Semantic reconstruction also adds a \texttt{MAXX} quantitative attribute to the spectrometer agent.
These placements are traceable to source lines, but they show that source-backed routing can still select scientifically questionable parent shapes for some attribute values.
The ChemSpectra draft keeps the \ac{NMR} spectral-data frame, but the unsupported 400~MHz instrument description and the \texttt{zg1p} plan remain in the draft.
The exact observed nucleus, \texttt{CDCl3} solvent, \texttt{zg30} pulse sequence, and observed frequency are still not preserved as explicit acquisition-level facts.

The next inspection step considers the semantic requirement checks described in the workflow and evaluates how the model interprets these schema-level expectations.
Across the inspected drafts, the activity evaluation target remains missing.
The datasets do contain broad measurement context, including spectra and signal acquisition.
They do not provide enough evidence to safely synthesize a concrete evaluated sample, compound, or studied process.
However, the ChemSpectra draft already contains \enquote{Signal Acquisition} as an input activity of the spectrum-generation activity.
The missing requirement therefore does not only reflect limited package metadata.
It also shows that the distinction between input activity and evaluated activity can become ambiguous in this profile shape.
The same acquisition process may be interpreted as prior process context, as the activity being characterized, or as both, depending on the intended modelling decision.

The attribute-parent check shows a similar limitation.
It can be marked fulfilled even when curator inspection still finds questionable placements, such as ChemSpectra extrema attached to the spectrometer agent.
The raw comparison runs reinforce this caution because the gemma3:27b run gives the pulse-program facts a more suitable parent shape than the gemma3:4b run, while the aggregate semantic score ranks the gemma3:4b run higher.
This suggests that the general-purpose models can often recognise schema-level roles, but they do not reliably apply domain expertise when deciding which scientific object a value should characterize.
The semantic checks themselves are also model-generated judgements over a model-generated draft.
Work on \ac{LLM}-as-a-judge evaluation describes such judgements as scalable but affected by biases and limited reasoning \cite{zheng2023llmjudge}.

Step assessment: Profile refinement and semantic evaluation are useful but limited.
They can attach traceable source-backed details and flag some structural gaps, especially when the core already gives them a suitable parent object.
They mostly enrich the provenance core that already exists instead of correcting its central interpretation.
The requirement report is therefore informative for directing curator review, but not for demonstrating reliable preservation of the curator-relevant acquisition facts.

\section{Vocabulary Querying and Grounding}
\label{sec:evaluation-grounding-observations}

Vocabulary querying is the step that tries to connect draft fields to established terms from vocabularies such as \ac{nmrCV} and \ac{QUDT}.
In plain terms, it does not search the original package again.
It only looks at fields that already exist in the draft and asks whether one of the available vocabulary terms is a good label for them.

The vocabulary mapping component is evaluated as a mostly independent workflow stage.
Previous stages determine how many vocabulary queries are produced and which field types are eligible for vocabulary queries.
The mapping decision itself can then be inspected from the query records, retrieved candidates, normalization decisions, and candidate-selection prompts.
For this reason, questionable upstream targets are not evaluated again in detail here.
They are treated as dependencies of the grounding stage.
In the current baseline artifacts, both package variants produce 25 vocabulary query records.
Comparison artifacts produce different query counts because their generated drafts contain different numbers and types of fields that can be grounded.

The pulse-program case shows the strongest positive pattern.
In the comparison run where the raw dataset contains a dedicated \enquote{Pulse Program} input entity, grounding receives a target that already matches the source signal.
The parent entity is mapped to the \ac{nmrCV} term \texttt{NMR pulse sequence}.
Its \texttt{Pulse Program Name} attribute preserves the source value \texttt{zg30}, while the flip-angle attribute is also recognised as an NMR pulse concept and mapped to \texttt{thirty degree pulse duration}.
The \texttt{ph31} setting remains ungrounded, which is acceptable because it is a specific phase-program value rather than a general vocabulary concept.
This example shows that grounding can produce plausible terms when the upstream profile shape gives it a precise target.
The mapping captures the controlled concept as \texttt{NMR pulse sequence}, while the vendor-specific program name \texttt{zg30} remains available as the source value.

Type grounding works across several levels of the generated profile.
At activity level, a ChemSpectra query for \texttt{NMR spectral data} and \texttt{1H NMR} selects the broader \ac{nmrCV} term \texttt{NMR spectrum}.
At agent level, a spectrometer query selects an NMR instrument term.
At attribute level, the raw-dataset query \texttt{NMR pulse program} with \texttt{zg30} selects \texttt{NMR pulse sequence}.
These examples indicate that the query formulation and candidate selection can identify domain-near terms from the available vocabulary.
They do not imply that every selected term is the most narrow candidate, because the selected term often normalizes the general concept rather than the exact source value.

Quantitative grounding is more constrained because \ac{QUDT} quantity kinds and units are cross-validated through triples of the form \texttt{<unit> qudt:hasQuantityKind <quantity-kind>}.
The flip-angle attribute in the pulse-program example shows both the value and the limitation of this guard.
Its domain-specific type is grounded through \ac{nmrCV} as \texttt{thirty degree pulse duration}, while the \ac{QUDT} quantity-kind and unit fields remain literal values.
During execution, the workflow retrieves generic angle concepts and a degree unit, but it does not write these fields because the selected candidates are not directly validated as a \texttt{qudt:hasQuantityKind} pair.
This is not simply failed grounding.
The case also shows a granularity mismatch between the domain value and the general quantity vocabulary.
\ac{QUDT} can represent the value as an angle, but it does not provide an NMR-specific quantity kind for a flip angle.
At the same time, the current validation rule is strict at the level of closely related \ac{QUDT} angle concepts such as \texttt{Angle} and \texttt{PlaneAngle}, which do not share the same connection to the \texttt{degree} unit.
The workflow therefore preserves the NMR-specific interpretation through \ac{nmrCV}, while the generic \ac{QUDT} quantity-kind and unit fields remain ungrounded.
The candidate sets also show that graph traversal is useful only as a constrained aid.
One-hop graph context helps the selector choose a broader parent term when many specific neighbours are retrieved, as in the pulse-sequence example.
The same expansion can introduce adjacent but wrong-domain candidates in broad vocabularies and in \ac{QUDT}.
Graph traversal should therefore support candidate interpretation, but it should not replace strict candidate rejection rules.

The diagnostic check supports the dependency-level interpretation of the grounding stage.
Observed nucleus, pulse sequence, frequency, and frequency unit retrieve close candidates once they are exposed as query targets.
Solvent and package-resource queries also retrieve relevant candidates, but with stronger ambiguity from adjacent reference-compound, conversion, and file-format terms.
Several missing final-draft facts are therefore not absent because no vocabulary candidate exists for them, but because they were not placed into fields that the grounding stage could query.

Step assessment: Vocabulary mapping is partly successful, but only for facts that already reached a queryable field.
It can normalize already placed fields and can abstain from several inappropriate mappings.
It does not repair missing facts, misplaced attributes, or an unsuitable provenance frame.
The grounded final drafts preserve the reconstructed profile shape and do not add missing source facts such as solvent, observed nucleus, the specific pulse-sequence value, or observed resonance frequency.
Vocabulary grounding is therefore best interpreted as a controlled-term normalization step over the current draft, not as an independent correction step for profile construction.
The retrieval step is also limited by the underlying embedding model, which is not specifically trained for \ac{NMR} metadata or catalysis terminology.
Domain-specific language models have been shown to improve scientific and materials text-mining tasks, and fine-tuned models have also been evaluated for chemical text mining including \ac{NMR} data extraction \cite{beltagy2019scibert,gupta2022matscibert,zhang2024chemicaltextmining}.
This suggests that a domain-adapted embedding or reranking model could sharpen candidate retrieval, but it would not remove the dependency on upstream profile construction.

Across the baseline evaluation, the strongest stages are those that preserve or locate source material.
The weaker stages are the ones that must decide where a fact belongs in the metadata structure.
The workflow is therefore useful as a diagnostic draft generator and review aid, but the inspected run does not yet support treating the generated draft as a reliable replacement for curator judgement.
