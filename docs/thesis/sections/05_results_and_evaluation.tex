\label{chap:results_and_evaluations}

The implemented prototype is evaluated as an end-to-end application for \ac{LLM}-assisted semantic metadata extraction from heterogeneous dataset packages.
The system is not limited to isolated prompt experiments.
Instead, it implements an executable workflow that connects dataset ingestion and preprocessing with evidence-backed metadata construction, semantic review, vocabulary grounding, and result inspection.
The primary evaluation focus is the automatically generated metadata draft without manual curation as a case study baseline.
It is examined how far a domain-agnostic \ac{DCAT-AP+} profile can carry the extraction of curator-relevant metadata before domain-specific profile extensions are introduced.
This work does not claim that schema-valid output is automatically scientifically correct.
Scientific correctness, curator time savings, and broad performance improvements over alternative systems would require additional evaluation or benchmark studies.
Therefore, a secondary focus is the software implementation itself.
A review on the usability of local models on commodity hardware is done.
This regards computing time and cost.
The effort for the vocabulary database curation is discussed.
The chapter closes by identifying the evaluation gaps that remain.

\section{Workflow Evaluation Setup}
\label{sec:evaluation-setup}

The evaluation is designed as an artifact-based diagnostic case study of the implemented workflow.
It inspects how selected metadata facts are preserved, transformed, omitted, or misplaced between the source packages and the automatically generated metadata draft.
The evaluation therefore follows the internal structure of the workflow as presented in \cref{tab:evaluation-framework-checklist}.

\begingroup
    \begin{center}
        \captionof{table}{Inspection focus for each workflow stage as evaluation checklist.}
        \label{tab:evaluation-framework-checklist}
    \end{center}

    \small
    \setlength{\parskip}{0.55em}
    \setlength{\parindent}{0pt}

    \textbf{Reference fact tracing}\\
    \hspace*{1em}source file locations; explicit and implicit statements

    \textbf{Preprocessing}\\
    \hspace*{1em}text preservation; chunk availability

    \textbf{Dataset overview}\\
    \hspace*{1em}early fact coverage; location hints; misleading overview statements

    \textbf{Evidence collection}\\
    \hspace*{1em}signal detection; category and role assignment; filtering impact

    \textbf{Provenance core construction}\\
    \hspace*{1em}coverage without chunk-level evidence; profile shape

    \textbf{Evidence routing}\\
    \hspace*{1em}entity assignment; relation assignment

    \textbf{Attribute construction}\\
    \hspace*{1em}generic attribute pattern; duplicate attributes; misplaced values

    \textbf{Semantic requirement evaluation}\\
    \hspace*{1em}\ac{LLM} judgements; unsupported semantic claims; curation needs

    \hspace*{1em}query formulation; retrieved terms; graph context; selected terms; rejected candidates

    \textbf{Overall workflow assessment}\\
    \hspace*{1em}cross-stage error patterns; reliable stages; development needs
\endgroup

The case study uses the two \textsuperscript{1}H \ac{NMR} package variants introduced in \cref{sec:dataset}.
Both packages originate from the same underlying measurement, but expose different metadata affordances.
The raw Bruker archive is closer to the instrument output and contains vendor-specific acquisition and processing files.
The ChemSpectra-derived export is closer to a repository-facing package and contains derived resources such as a \ac{JCAMP-DX} spectrum, a rendered spectrum image, and a textual dataset description.
The comparison therefore does not evaluate different scientific measurements, but how different representations of the same measurement affect source accessibility, evidence traceability, provenance representation, and profile construction.

As an inspection reference, a small set of curator-relevant facts is defined before interpreting the workflow output.
For the present measurement, these facts include the dataset identity as \textsuperscript{1}H \ac{NMR} data, the observed nucleus, solvent or reference information, pulse sequence, instrument description, observed resonance frequency, and the distinction between raw and derived package resources.
The observed frequency is treated as a specific acquisition value of the \textsuperscript{1}H channel, recorded in the source files as approximately 500.13~MHz, rather than only as the nominal 500~MHz instrument description.
These facts were selected because they provide basic acquisition and package-context information that supports curator review of an \ac{NMR} dataset \cite{Schober2018nmrML}.
The reference expectation is not a formal metadata standard.
It is a scoped inspection aid for evaluating whether the automatically generated draft contains reviewable, evidence-aware structure.

Across the evaluation, followed facts are described with the labels \emph{placed}, \emph{partial}, \emph{misplaced}, \emph{absent}, and \emph{not available in package}.
A fact is treated as \emph{placed} when it appears in an appropriate part of the generated profile.
It is \emph{partial} when it is present but underspecified or represented only at a coarse level.
It is \emph{misplaced} when it is represented under an inappropriate entity, role, relation, or attribute structure.
It is \emph{absent} when it is available in the source package or intermediate artifacts but not represented in the final draft.
It is \emph{not available in package} when the corresponding package representation does not contain the required information.
These labels are qualitative inspection categories, not statistically validated performance metrics.
They are applied within the case study to identify where facts are preserved, lost, or incorrectly transformed.
The evaluation can therefore support claims about observed workflow behaviour, traceability, and development needs in the selected case.
It cannot support general claims about extraction accuracy, curator time savings, scientific correctness, or superiority over other systems without additional expert evaluation or benchmark studies.

\section{Baseline Evaluation}
\label{sec:evaluation-baseline-run}

\subsection{Reference Fact Tracing}
\label{sec:evaluation-reference-fact-tracing}

The reference fact tracing step establishes which selected facts are available in the original source package contents before automatic metadata construction.
The inspected reference facts focus on whether the packages expose the measurement as \textsuperscript{1}H \ac{NMR} data, identify the observed nucleus, preserve solvent or reference information, name the pulse sequence and instrument, report the observed resonance frequency, and distinguish raw from derived resources.

In the raw dataset, the dataset identity is available through Bruker acquisition and processing files and through the human-readable title file \texttt{10/pdata/1/title}.
The observed nucleus is explicitly recorded in the acquisition files \texttt{10/acqus} and \texttt{10/acqu} as \texttt{NUC1=<1H>}.
The same acquisition context also records the solvent as \texttt{SOLVENT=<CDCl3>} and the pulse sequence as \texttt{PULPROG=<zg30>}, while the pulse-program file provides the corresponding program content.
Instrument information is available in \texttt{10/uxnmr.info}, which identifies an \texttt{Avance III NMR spectrometer} and reports a rounded \texttt{1H-frequency: 500.13 MHz}.
The more specific observed resonance frequency is present in the acquisition files as \texttt{SFO1=500.133088507478}.
The raw package also contains the binary \texttt{fid} signal, acquisition files, processing files, shim values, audit trail, pulse program, and instrument configuration.

In the ChemSpectra export, the dataset identity is stated in \texttt{dataset\_description.txt} as \texttt{dataset name: 1H NMR} and is also implied by the \ac{JCAMP-DX} spectrum file.
The \texttt{10.edit.jdx} file records the observed nucleus, the \texttt{CDCl3} solvent or reference information, the \texttt{zg30} pulse sequence, and the observed frequency \texttt{500.133088507478}.
The instrument description is available in the textual dataset description as \texttt{Bruker Avance 500 MHz}.
Compared with the raw dataset, the relevant metadata in this package is concentrated in the \ac{JCAMP-DX} spectrum file and the textual dataset description.

\subsection{Preprocessing}
\label{sec:evaluation-preprocessing-observations}

To begin the evaluation, the preprocessing step is inspected to determine whether the selected reference facts are preserved in the chunk-level evidence.
The evaluated runs use the gate parameters described in \cref{sec:preprocessing}.
These settings are relevant for the present \textsuperscript{1}H \ac{NMR} packages because many metadata facts appear as compact parameter records rather than prose.
The raw observed-frequency value \texttt{SFO1= 500.133088507478} illustrates why structured parameter lines survive the gate.
Its score is calculated as sum of tunable scoring features for reasonable word length, structured-text syntax, and digit density.
For this line, the gate extracts the alphabetic token \texttt{SFO}, which gives an average word length of three characters and adds \texttt{0.10} for \texttt{reasonable\_word\_length}.
The line also matches the structured-text pattern \texttt{key = value}, because \texttt{SFO1} is followed by \texttt{=} and a non-empty value.
This adds the configured structured-text bonus of \texttt{0.70}.
At the same time, the line has a high digit ratio: 16 of 24 characters are digits, resulting in a ratio of approximately \texttt{0.67}.
Since this exceeds the configured \texttt{digit\_ratio\_threshold} of \texttt{0.45}, the gate subtracts \texttt{0.25} for \texttt{too\_many\_digits}.
The resulting score is therefore \texttt{0.10 + 0.70 - 0.25 = 0.55}, which is above the configured \texttt{keep\_threshold} of \texttt{0.30}.
This preservation result is limited to the presented packages, because the text-quality gate is tunable and was inspected here only for this \textsuperscript{1}H \ac{NMR} case.

The baseline chunking step uses fixed-token chunking with a target and maximum size of 1024 tokens.
This strategy is used for the detailed qualitative inspection because it is faster than semantic chunking and keeps chunks within a size range suitable for the local \ac{LLM} models used in this work.
It produces 32 individual chunks for the raw dataset across 15 source files and 244 individual chunks for the ChemSpectra export across three textual sources.
The raw binary \texttt{fid} file and the rendered ChemSpectra image remain package resources, but they do not become substantive textual chunk content.
In the raw dataset, chunked acquisition files preserve \texttt{NUC1= <1H>}, \texttt{PULPROG= <zg30>}, \texttt{SFO1= 500.133088507478}, and \texttt{SOLVENT= <CDCl3>}.
A separate chunk preserves the instrument context, including \texttt{Avance III NMR spectrometer} and the rounded \textsuperscript{1}H frequency of 500.13~MHz.
The main limitation is not fact loss, but fact separation.
Observed nucleus, observed frequency, and solvent or reference information therefore belong to the same acquisition and interpretation context.
\ac{nmrCV} treats instrument configuration, sample information such as solvent and reference standards, acquisition settings, and raw spectral data as connected metadata needed to describe and reconstruct an NMR experiment \cite{Schober2018nmrML}.
In the raw baseline chunks, observed nucleus and pulse-sequence information can appear in neighbouring chunks rather than in the same chunk as solvent and observed frequency.
In the ChemSpectra baseline chunks, the observed frequency appears in the first \ac{JCAMP-DX} header chunk, while observed nucleus, solvent or reference information, and pulse sequence appear in the following chunk.

Semantic chunking is used as a comparison to test whether such fact splitting is reduced.
It generates embeddings with \texttt{qwen3-embedding:0.6b} over two-line buffer windows and applies a 128-token minimum, a 1024-token maximum, and a 95th percentile similarity cut-off.
With this strategy, the raw dataset produces 51 individual chunks and the ChemSpectra export produces 42 individual chunks.
For the raw dataset, semantic chunking still separates some acquisition facts across adjacent parameter-file chunks.
For the ChemSpectra export, the main \ac{JCAMP-DX} header facts are kept together in one chunk.
In this case, semantic chunking leads to a different distribution of ChemSpectra header information, with some related facts appearing in the same chunk rather than across separate chunks.
This observation can become relevant for later evidence extraction, because the \ac{LLM} can only reason over the content of a single chunk at a time.

\subsection{Dataset Overview}
\label{sec:evaluation-overview-observations}

The dataset overview stage was inspected as orientation output before evidence collection.
It is not treated as source evidence for the reference facts.
Instead, it is evaluated according to whether it points later extraction steps toward files that are likely to contain relevant information.
This distinction matters because the overview works at file and package level, while the reference facts often occur as compact parameter records inside individual files.

For the raw dataset, the baseline overview gives source-location guidance.
The two direct acquisition files are ranked first and second.
Both are summarized as files that contain \enquote{parameter settings for a Bruker NMR experiment} and that configure the instrument and experimental conditions.
This correctly identifies the acquisition files as important locations for later evidence extraction.
However, the summary remains generic.
It does not expose the concrete values \texttt{NUC1=<1H>}, \texttt{SOLVENT=<CDCl3>}, \texttt{PULPROG=<zg30>}, or \texttt{SFO1=500.133088507478}.

Other raw files are also described at file-role level.
The pulse-program file is described as a \enquote{Bruker NMR pulse program}, which points to the pulse-sequence evidence location, but the overview does not preserve the concrete \texttt{zg30} value.
The instrument-configuration file is summarized as containing \enquote{configuration information for a Bruker Avance III NMR spectrometer}, which correctly identifies an instrument-context source.
The rounded \textsuperscript{1}H frequency value is still not surfaced by the overview.
The binary signal file is described as raw \ac{NMR} data in a likely proprietary format with empty sampled content.
This supports the distinction between raw data and textual metadata, but it does not add acquisition values.
The overview also assigns broad acquisition, processing, and instrument-setting roles to several parameter files, so the resulting orientation is not sharply separated by scientific metadata role.

For the ChemSpectra export, the overview identifies the textual description as a dataset description containing instrument information and a file list.
It also identifies the \ac{JCAMP-DX} file as a \textsuperscript{1}H \ac{NMR} spectrum with spectral parameters, XY data points, and an automatically generated peak table.
This is the most important location hint for later extraction because the selected acquisition facts are concentrated in that spectrum file.
Nevertheless, the overview does not preserve the exact observed nucleus, the \texttt{CDCl3} solvent or reference information, the \texttt{zg30} pulse sequence, or the observed frequency as separate facts.

Overall, the dataset overview stage provides file-location guidance and package orientation.
It can identify the acquisition files, pulse-program file, instrument-configuration file, raw signal file, textual dataset description, and \ac{JCAMP-DX} spectrum as relevant resources.
It should not be read as value-level fact extraction.
The selected acquisition facts still have to be checked in chunk-level evidence, where the workflow has access to the relevant source lines rather than only file summaries.

\subsection{Evidence Collection}
\label{sec:evaluation-evidence-collection-observations}

The first inspection basis for this stage is the raw dataset evidence-note output of the baseline configuration.
This output contains 120 portable notes, 59 contextual notes, and 9 rejected candidate notes.
The portable notes are concentrated in the categories \texttt{resource\_signal}, \texttt{instrument\_signal}, and \texttt{measurement\_signal}.
The most frequent portable roles are \texttt{parameter} and \texttt{descriptor}, followed by smaller numbers of \texttt{qualitative\_attribute}, \texttt{identity}, and \texttt{context} roles.
The stage therefore produces a broad signal inventory, but the inventory is still organized through coarse workflow categories rather than domain-specific \ac{NMR} concepts.

Several reference facts are detected at chunk level.
The pulse sequence is detected directly from \texttt{10/acqu} as the claim that the \ac{NMR} experiment uses the \texttt{zg30} pulse program, with \texttt{PULPROG=<zg30>} as evidence text.
The solvent is detected directly from \texttt{10/acqus} as the claim that the solvent is \texttt{CDCl3}.
The instrument description is detected from \texttt{10/uxnmr.info} as the claim that the spectrometer is an \texttt{Avance III NMR spectrometer}.
The same source context also contains the rounded \textsuperscript{1}H frequency value of 500.13~MHz.
These observations show that evidence collection can find acquisition and instrument signals that were only indicated at file level in the overview.

At the same time, the evidence notes show that detection and semantic placement are not identical.
The \texttt{CDCl3} solvent note is assigned to \texttt{instrument\_signal} with the role \texttt{parameter}.
The source line is therefore found, but the assigned category does not express the curator-facing concept of solvent or reference information.
The precise observed-frequency value \texttt{SFO1=500.133088507478} is detected in the evidence artifacts, but it is not retained as a clean portable evidence note.
The observed-nucleus value \texttt{NUC1=<1H>} is detected as a direct candidate note, but it is removed by deterministic lexical deduplication over short structured parameter lines.
It is merged into a retained \texttt{PULPROG=<zg30>} note, even though the two source facts are not semantically equivalent.
The observed loss of \texttt{NUC1=<1H>} indicates that lexical deduplication is too permissive for compact structured parameter records.
In this case, unrelated \texttt{key=value} facts are grouped because they share short syntactic patterns, although they describe different acquisition properties.

The contextual evidence contains neighbouring signals that are technically grounded but less relevant to the selected reference facts.
Examples include channel states such as \texttt{NUC2=<off>} through \texttt{NUC8=<off>}.
The pulse-program file also contributes contextual method information, including a 30 degree flip angle and a 1D program type.
These notes show that compact instrument files produce many neighbouring signals around the facts selected for evaluation.

The main observation for this stage is that several selected facts are still detected before profile construction.
However, the coarse category set does not always express the domain role that a curator would assign to the same source line, echoing ontology work in catalysis where reaction roles and catalyst relations require explicit semantic modelling \cite{behr2024reac4cat}.
This suggests two development directions for ongoing work.
Domain terms may need to be available already during evidence extraction, instead of being introduced only during vocabulary grounding, as \ac{LLM}-based catalysis text mining also relies on domain knowledge injection and user-specified extraction schemas \cite{walls2025catminer}.
Alternatively, the category harness could be loosened so that the model can emit labels closer to the source signal, such as solvent, observed nucleus, pulse sequence, or observed frequency, following extraction designs that separate open extraction from later schema definition and canonicalization \cite{zhang2024edc}.
That direction would require more explicit downstream routing logic, because later stages could no longer rely only on the current fixed category set.
Another development direction is a model or component trained specifically for metadata-signal detection, as chemical text-mining work has shown for tasks including NMR data extraction \cite{zhang2024chemicaltextmining}.
Such a component could include \ac{NER}-style recognition of domain terms and parameter-value pairs, following chemistry-aware extraction pipelines for entities, properties, measurements, and relationships \cite{swain2016chemdataextractor}.


\subsection{Provenance Core Construction}
\label{sec:evaluation-core-construction-observations}

The provenance core is inspected before attribute construction, semantic reconstruction, and vocabulary grounding.
This stage does not receive the evidence notes inspected above as direct input.
It is constructed from the dataset overview artifacts and the current dataset-level draft.
The inspection therefore evaluates whether the overview representation is sufficient to create the main activity skeleton.
It does not evaluate whether all previously detected evidence notes are preserved.

In the baseline configuration with fixed 1024-token chunks and the 12b model, the raw dataset core is framed as \texttt{NMR Experiment Data}.
It creates one activity titled \enquote{NMR Data Acquisition and Processing}.
The activity describes automated instrument control and data acquisition using Bruker TopSpin software.
It places \texttt{Bruker TopSpin} as technical agent, parameter files and shim values as inputs, audit trail generation as a preceding activity, and \texttt{NMR Experiment Data (FID)} as output.
This gives the raw package an acquisition-oriented provenance core and preserves the raw signal as a central data output.
At the same time, the core does not preserve \texttt{NUC1=<1H>}, \texttt{CDCl3}, \texttt{zg30}, or \texttt{SFO1=500.133088507478} as explicit value-level facts.

The ChemSpectra export behaves differently in the same baseline configuration.
Its core is framed as \texttt{Records Dataset} and contains one activity titled \enquote{Records Dataset Generation}.
The activity is described as the creation of a description file and a JSON structure.
It places \texttt{Text Editor} and \texttt{JSON Editor} as agents, \texttt{Dataset Description} as input, and \texttt{Records Dataset} as output.
This loses the \textsuperscript{1}H \ac{NMR} spectrum as the central data product at the provenance-core stage.
It also does not preserve the \ac{JCAMP-DX} spectrum, observed nucleus, solvent or reference information, pulse sequence, or observed frequency as core-level facts.
The baseline contrast shows that the same workflow configuration creates different provenance interpretations for the two package representations.
The raw package is interpreted as an acquisition dataset, while the ChemSpectra export is interpreted as generic record generation.

Additional runs are treated only as robustness observations.
They show that the provenance core is sensitive to run configuration, but they do not support a causal claim about model size or chunking method because the evaluation does not contain repeated controlled runs.
With the 27b model, the ChemSpectra export is framed as \texttt{1H NMR Spectra of Organic Compounds} and \texttt{NMR Data Generation}, which preserves the \ac{NMR} spectrum frame more clearly than the baseline.
With semantic chunking and the 12b model, the same package drifts toward \texttt{Process Operational Characteristics}, which loses the \ac{NMR}-specific provenance interpretation.
For the raw dataset, additional 27b and semantic-chunking runs remain more measurement-oriented than another configuration-centered run, but they differ in how they organize spectra, audit trails, titles, parameters, and pulse-program resources.
A separate comparison between a 4b model and a 27b model on the raw dataset again shows different core specificity.
The 4b model produces a generic \texttt{NMR} and \texttt{data processing} frame, while the 27b model produces a more specific \texttt{Bruker Avance III NMR Spectral Data} and \texttt{NMR Data Generation} frame.

The observations show that provenance core construction is mainly an early provenance-framing step, not a value-extraction step.
Its output follows the dataset overview strongly.
When the overview foregrounds acquisition and raw data resources, the core can become measurement-oriented.
When the overview foregrounds description files, JSON placeholders, or generic records, the core can drift toward file-production or record-generation interpretations.
The main curation concern at this stage is therefore the central activity and output interpretation, because later value placement starts from this core structure.

\subsection{Evidence Routing}
\label{sec:evaluation-routing-observations}

\begin{itemize}
    \item Evaluation basis: comparison between generated core structure, attribute placement, reconstructed draft, and evidence-routing records.
    \item Raw dataset: evidence is routed into a coherent activity-input-output shape around acquisition and processing.
    \item Raw dataset: no explicit evaluated entity is created for the activity.
    \item ChemSpectra export: evidence is routed into a file-generation shape rather than an NMR-measurement shape.
    \item ChemSpectra export: the instrument evidence is later routed to the technical-agent position, but the broader activity frame remains record generation.
    \item Observation: evidence routing can improve individual placements while leaving the central activity interpretation unchanged.
\end{itemize}

\subsection{Attribute Construction}
\label{sec:evaluation-attribute-observations}

\begin{itemize}
    \item Evaluation basis: attribute construction output and reconstructed profile draft.
    \item Raw dataset: attribute construction does not preserve the selected reference facts as explicit attributes in the attribute draft.
    \item Raw dataset: reconstruction adds a temperature value to the activity and keeps additional quantitative attributes on \texttt{Bruker TopSpin} and parameter-file parents.
    \item ChemSpectra export: attribute construction attaches the instrument as a qualitative attribute.
    \item ChemSpectra export: reconstruction adds a numeric solvent peak value to the activity, but does not preserve \texttt{CDCl3} as solvent or reference.
    \item Observation: attribute construction captures some local numeric values.
    \item Observation: important curator-facing acquisition facts are still absent or under-specified.
\end{itemize}

\subsection{Vocabulary Querying and Grounding}

    \item Evaluation basis: vocabulary queries, grounding decisions, and grounded final drafts.
    \item Raw dataset: grounding produces 35 vocabulary query records.

\subsection{Overall Workflow Assessment}
\label{sec:evaluation-overall-observations}

\begin{itemize}
    \item Evaluation basis: cross-stage comparison from source facts through chunks, evidence, profile drafts, requirement reports, grounding, and final drafts.
    \item Raw dataset: the workflow preserves a coherent NMR acquisition and processing story.
    \item Raw dataset: the final draft preserves the raw \texttt{fid} output and related parameter resources.
    \item Raw dataset: specific acquisition facts such as \texttt{CDCl3}, \texttt{zg30}, and \texttt{500.133088507478} are available in the source material but absent or only partial in the final draft.
    \item ChemSpectra export: the workflow detects many key NMR facts during evidence extraction.
    \item ChemSpectra export: the final draft keeps only coarse NMR identity and instrument information while losing solvent, pulse sequence, observed nucleus, observed frequency, and the central derived-spectrum resource framing.
    \item ChemSpectra export: the major failure pattern is not source availability but transformation from detected evidence into the profile core.
    \item Observation: the baseline supports claims about traceable workflow behavior and diagnostic inspection, but not claims about complete metadata accuracy.
\end{itemize}
