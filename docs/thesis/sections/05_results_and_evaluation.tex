\label{chap:results_and_evaluations}

This chapter evaluates the implemented prototype as an end-to-end application for \ac{LLM}-assisted semantic metadata extraction from heterogeneous dataset packages.
The system is not limited to isolated prompt experiments, but implements an executable workflow that connects dataset ingestion and preprocessing with evidence-backed metadata construction, semantic review, vocabulary grounding, and result inspection.
The evaluated output is the automatically generated metadata draft before manual curation.

The chapter treats this output as both a software result and a case-study baseline.
It examines how far a domain-agnostic \ac{DCAT-AP+} profile can carry the extraction of curator-relevant metadata before domain-specific profile extensions are introduced.
Using \ac{DCAT-AP+} as the initial profile is central to this interpretation.
The profile provides a general semantic structure for describing datasets, distributions, provenance, activities, agents, entities, and quantitative attributes without requiring a customized domain profile at the outset.
The generated metadata drafts can therefore be read as baseline extraction results.
They show which dataset facts can already be represented through a reusable profile foundation and where later domain-specific extensions would be needed to capture scientific meaning more precisely.

The evaluation focuses on metadata accessibility and workflow inspectability.
It asks whether the workflow can turn heterogeneous source packages into profile-compatible metadata drafts, whether important source facts are represented in appropriate parts of the \ac{DCAT-AP+} structure, and whether intermediate artifacts make omissions, repairs, and evidence use visible.
It does not claim that schema-valid output is automatically scientifically correct.
Scientific correctness, curator time savings, and broad performance improvements over alternative systems would require additional expert evaluation or benchmark studies.

The chapter first defines the case-study setup and the curator-oriented reference expectation.
It then evaluates the generated metadata drafts, package affordances, persisted interim artifacts, semantic requirement outcomes, and vocabulary grounding results.
The chapter closes by identifying the evaluation gaps that remain.

\section{Evaluation Setup}
\label{sec:evaluation-setup}

The evaluation setup defines the dataset inputs, the curator-oriented reference expectation, and the interpretation frame for the results.
It does not measure general extraction accuracy across many datasets.
Instead, it examines how the implemented workflow behaves on the two \textsuperscript{1}H \ac{NMR} package variants introduced in \cref{sec:dataset}.
The focus is on metadata accessibility and workflow inspectability.
The evaluation asks whether the workflow can turn heterogeneous source packages into profile-compatible metadata drafts, whether important source facts are represented in appropriate parts of the \ac{DCAT-AP+} structure, and whether intermediate artifacts make omissions, repairs, and evidence use visible.

The two evaluation inputs originate from the same underlying measurement but expose different metadata affordances.
The raw Bruker archive is closer to the instrument output and preserves detailed acquisition and processing context in vendor-specific files.
The ChemSpectra-derived export is closer to a repository-facing package and contains derived representations such as a \ac{JCAMP-DX} spectrum, a rendered spectrum image, and a textual dataset description.
The comparison therefore does not evaluate different scientific measurements.
It evaluates how different package representations of the same measurement affect metadata extraction and provenance representation.

For the purpose of this evaluation, a helpful result is defined from the perspective of a dataset curator who wants to make the dataset more accessible through a structured metadata profile.
This reference expectation is not a formal gold standard and does not require a complete scientific interpretation of the spectrum.
Instead, it describes the kind of metadata draft that would support later review and publication.
Such a draft should identify the dataset as a \textsuperscript{1}H \ac{NMR} dataset, describe the available distributions, capture central acquisition context where it is present, distinguish raw source files from derived representations, and keep generated claims inspectable through source evidence.

The expected acquisition context includes facts such as the observed nucleus, solvent or reference, pulse sequence, and observed resonance frequency.
For the present measurement, the observed frequency is treated as a specific acquisition value of the \textsuperscript{1}H channel, recorded in the source files as approximately 500.13~MHz, rather than only as the nominal 500~MHz instrument description.
These facts are relevant for \ac{NMR} metadata because they provide basic acquisition context and help distinguish raw, processed, and exchange-oriented representations of the measurement \cite{Schober2018nmrML}.
The purpose of the reference expectation is not to require that every possible instrument parameter is extracted.
Rather, it defines the level of structured, evidence-aware description that would make the package easier to review, correct, and publish.

The evaluation does not claim that schema-valid output is automatically scientifically correct.
Scientific correctness, curator time savings, and broad performance improvements over alternative systems would require additional expert evaluation or benchmark studies.

\section{Baseline Results}
\label{sec:baseline-results}

\subsection{Raw Bruker Package}
\label{subsec:baseline-raw-bruker}

The raw Bruker package is metadata-rich but not curator-ready.
It contains acquisition and processing parameter files, an audit trail, a pulse program, instrument-related files, and the binary free induction decay.
These files expose important facts such as the experiment type, observed nucleus, solvent, pulse sequence, acquisition time, approximate spectrometer frequency, number of scans, time-domain point count, and processing parameters.
However, these facts are distributed across vendor-specific files and parameter names.
They are therefore available to a domain-aware reader or extraction workflow, but they are not already represented as a reusable dataset metadata record.

\subsection{ChemSpectra Export Package}
\label{subsec:baseline-chemspectra}

The ChemSpectra export package is smaller and more access-oriented.
It contains a JCAMP-DX spectrum, a rendered spectrum image, an inferred \ac{JSON} file, and a textual dataset description.
The JCAMP-DX file exposes publication-facing spectral metadata such as the observed frequency, observed nucleus, solvent or shift reference, pulse sequence, axis units, and number of points.
The textual description names the dataset and instrument and lists the exported files with checksums.
At the same time, the package omits the nested raw archive, so the richer acquisition and audit context of the Bruker export is no longer directly available.

\subsection{Baseline Comparison}
\label{subsec:baseline-comparison}

The two package variants therefore represent complementary baselines.
The raw Bruker package has stronger technical and provenance coverage, but its metadata is embedded in a vendor-specific structure.
The ChemSpectra export has stronger accessibility as a repository-facing package, but it contains less source context for reconstructing the original acquisition process.
Neither package is already a \ac{DCAT-AP+} metadata artifact.
The workflow result must therefore be evaluated by asking whether it can make the accessible structure of the ChemSpectra export and the technical depth of the Bruker archive available in a curator-reviewable profile draft.

\section{Workflow Results}
\label{sec:workflow-results}

\subsection{Final Metadata Drafts}
\label{subsec:final-metadata-drafts}

The final metadata drafts are evaluated against the curator-oriented reference result defined above.
The analysis considers whether each draft identifies the dataset appropriately, represents available distributions, captures central experimental context, and keeps the generated structure compatible with the selected \ac{DCAT-AP+} profile.
The comparison between the raw Bruker and ChemSpectra runs is especially important because the same underlying measurement is exposed through different source artifacts.

\subsection{Interim Artifacts}
\label{subsec:interim-artifacts}

The persisted interim artifacts are evaluated as part of the workflow result.
They show how the final draft emerged from file summaries, evidence notes, generated draft stages, semantic requirement checks, reconstruction outputs, validation reports, and vocabulary grounding records.
This makes it possible to distinguish between facts that were absent from the source package, facts that were present but not selected as evidence, and facts that were selected but not placed in the final metadata structure.

\subsection{Requirement Evaluation Outcomes}
\label{subsec:requirement-outcomes}

The semantic requirement outcomes are used to inspect whether the generated draft satisfies profile-level expectations beyond schema validity.
These outcomes are particularly useful for identifying dataset-title problems, description-scope problems, weak generation activities, missing method plans, technical-agent confusion, attribute-range issues, and attribute-placement errors.
They therefore provide a bridge between the mechanical validity of the generated \ac{JSON} artifact and the curator-oriented question of whether the result is meaningful and reviewable.

\section{Evaluation Gaps}
\label{sec:evaluation-gaps}

The evaluation remains limited in scope.
It is based on a small number of package variants and does not establish broad extraction accuracy across scientific domains.
It also does not measure curator time savings or prove scientific correctness of the generated metadata.
The results should therefore be interpreted as a baseline for domain-agnostic \ac{DCAT-AP+} extraction and as a starting point for later work on domain-specific profile extensions, expert validation, and larger benchmark studies.
