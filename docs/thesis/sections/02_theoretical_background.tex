\label{chap:background}

In order to develop a workflow that can extract metadata from arbitrary catalysis datasets and represent it in a standardised, machine-actionable form, it is necessary to understand the scientific context of the data to be extracted, as well as the technical foundations of the system that will execute the workflow.
The first section introduces the landscape of data in catalytic experiments, motivating the need for application-specific schemas as a metadata standard.
After that, a short section presents metadata standards on a conceptual level.
As these standards should align with common rules, the third section introduces semantic web technologies as a toolset for representing and connecting the data in a machine-actionable form, as well as providing a common language with which to formulate the standards.
The fourth section provides background on large language models (LLMs), as this work aims to utilize their capabilities to extract information from an unstructured, human-readable form into any specified format.

\section{Catalytic Experiments}
\label{sec:catalytic-experiments}

Catalysis refers to the acceleration of a chemical reaction by a substance that participates in the reaction but is not consumed by it.
A catalyst can lower the effective activation barrier and allow a reaction to proceed under milder or more technically useful conditions, as schematically shown in Figure~\ref{fig:catalysis-activation-energy}.
Consequently, catalysts are widely studied across application fields such as energy cost reduction, environmental recovery, chemical manufacturing, and materials science \cite{osman2024coordination}.
Catalytic experiments investigate how catalysts are prepared, activated, characterized, and used to transform reactants under defined reaction conditions.
The resulting data landscape is therefore not limited to final performance indicators, but spans the full experimental chain from catalyst synthesis to functional analysis \cite{marshall2023digital}.

\subsection{Catalytic Data and Metadata}
\label{sec:catalytic-data-metadata}

During the life cycle of a catalyst, a precursor may be transformed into an activated material and subsequently into a spent or deactivated sample. Each stage in this process can yield new characterisation and performance data, which must be linked to the corresponding material state \cite{mendes2025data}.
For this reason, a catalytic result such as a conversion, selectivity, yield, or reaction rate is only interpretable together with relevant metadata \cite{wulf2021unified}.
Table~\ref{tab:catalytic-data-landscape} summarizes this landscape by grouping representative data and metadata into material, preparation, characterization, reactor, operating, and performance-related categories. These categories indicate which contextual links have to be preserved when heterogeneous datasets and kinetic measurements, are interpreted together \cite{mendes2025data,schumann2025nomad,stroemert2026chemdcat}.

\input{tables/catalytic_data_landscape}

Experimental metadata describe the context in which primary data were generated, processed, and interpreted. In catalytic experiments, this includes sample provenance, instrument settings, calibration procedures, and processing choices. Such information is not just a secondary annotation layer, but rather an integral part of the scientific evidence, because the same numerical activity value can have a different meaning when the catalyst pretreatment or analytical calibration changes \cite{wulf2021unified}. Metadata therefore turn isolated measurements into documented experimental records and provide the basis for reproducing experiments or comparing evaluation studies across different catalysts, reactors, and laboratories \cite{wulf2021unified,salim2026methane}. In automated catalyst testing, they also keep raw data, evaluated data, standard operating procedures, and database entries connected throughout the experimental workflow \cite{moshantaf2024advancing}.

\subsection{NMR Spectroscopy Data}
\label{subsec:nmr-spectroscopy-data}

Nuclear magnetic resonance (NMR) spectroscopy is a common analytical method for characterising chemical samples and following transformations in reaction systems. In a catalytic experiment, NMR data may describe the identity of products, the presence of intermediates or impurities, changes in reactant concentration, or the state of catalyst-related molecular species \cite{marshall2023digital,mendes2025data}. Within the catalytic data landscape, NMR therefore belongs primarily to the characterization category, while quantitative reaction monitoring also links it to performance data \cite{mendes2025data}.

An NMR experiment typically produces raw time-domain data, commonly represented as a free induction decay, which are processed into a frequency-domain spectrum. The resulting spectrum distributes signal intensity over a chemical-shift axis, usually reported in parts per million \cite{nmrmlSpecification}. Rather than forming a single scalar measurement, the data contain peaks, peak groups, integrals, multiplicities, coupling patterns, and background components such as noise, baseline drift, solvent signals, or processing artefacts. Two-dimensional NMR experiments additionally record correlations across two frequency axes \cite{nmrmlSpecification}. In practice, NMR datasets are often distributed as instrument-specific directory structures containing the raw signal and acquisition parameters side by side. They may also include processed spectra, exchange formats such as JCAMP-DX, peak or integration tables, and graphical previews \cite{nmrmlSpecification,steinbeck2023nfdi4chem}. This makes NMR an instructive example for metadata extraction, because the relevant signals include the evaluated entities as well as the contextual information of the data generating experiment \cite{nmrmlSpecification,steinbeck2023nfdi4chem}.

For semantic metadata extraction, NMR therefore illustrates why a dataset record has to preserve the link between measured arrays, derived peak tables, processing steps, instrument settings, sample state, and the catalytic experiment in which the measurement was taken \cite{stroemert2026chemdcat,chemdcatapDocumentation}.
Profiles such as ChemDCAT-AP and vocabularies such as nmrCV provide a route for representing these links in a machine-actionable way instead of leaving them implicit in file names, figure captions, or supplementary text \cite{stroemert2026chemdcat,chemdcatapDocumentation,nmrmlSpecification}.

\section{Metadata Standards}
\label{sec:metadata-standards}

As the previous section demonstrated, catalytic measurements only become scientifically useful when they are connected to their experimental context.
Metadata standards address this need by defining how such context should be documented in a consistent, reusable way.
Conceptually, a metadata standard specifies the expected information, how it should be structured and how values should be expressed, enabling records to be interpreted beyond the laboratory in which they were created \cite{wulf2021unified,mendes2025data}.

Therefore, a metadata standard establishes a shared framework for reporting on the entities, activities, quantities, units, methods, instruments and provenance relations required to comprehend a dataset.
Some requirements describe the minimum information necessary for an experiment to be interpreted, compared, or reproduced.
Other requirements concern consistency, stipulating that values use stable units, controlled terms, identifiers and data types instead of uncontrolled local wording.
In this sense, a standard establishes an agreement between data producers and users regarding what constitutes sufficient context for reuse \cite{wulf2021unified,steinbeck2020nfdi4chem}.

This agreement is particularly important for automated metadata extraction.
While an extraction system can identify candidate values in files, tables, captions, or instrument exports, it still requires a target structure in which these values can be placed.
The standard provides this target structure, distinguishing, for instance, whether an extracted phrase refers to a sample, an instrument, a measured quantity, a processing step or a data-generating activity.
The standard also enables validation, allowing generated metadata records to be checked for missing required fields, incompatible units, unsupported value types or relations that do not fit the expected model \cite{w3c2017shacl,stroemert2026chemdcat}.

\section{Semantic Web Technologies}
\label{sec:semantic-web-technologies}
Semantic web technologies provide the representation languages, identifiers, vocabularies and validation mechanisms that enable standards to be implemented in a machine-actionable form.
Their central idea is to move from a web of human-readable documents to a web of data whose meaning is explicitly described for computational processing \cite{jannidis2017digitalhumanities}.


\subsection{Semantic Modelling of Domain Knowledge}
\label{sec:semantic-modelling-domain-knowledge}

A semantic model distinguishes between general concepts and concrete entities.
General concepts are represented as classes, such as \textit{Catalyst}, \textit{Catalytic Reaction}, or \textit{Reaction Condition}, while individual objects or events are represented as instances of these classes.
A specific iron-based catalyst can therefore be modelled as an instance of the class \textit{Catalyst}, and a particular methane conversion experiment as an instance of the class \textit{Catalytic Reaction}.
Relations connect these instances and express domain-specific statements, for example that a reaction uses a certain catalyst, occurs under a defined temperature, or produces a specific product.
Additional values, such as names, numerical measurements, or timestamps, can be attached as descriptive properties.
Together, these elements form a graph-like representation in which domain entities are described not only by their individual attributes, but also by their semantic context \cite{stuckenschmidt2011ontologien,wulf2021unified}.

Ontologies provide a formal specification of such semantic models.
They define the concepts that are relevant to a domain, organise them into class hierarchies, and describe the relations that may hold between them.
In addition, ontologies can express axioms that restrict or clarify the meaning of these concepts and relations, for example by declaring that every \textit{Catalyst} is a type of \textit{Material}, that two classes are disjoint, or that a particular relation can only connect certain kinds of entities.
Ontologies can be distinguished into upper ontologies, which provide general, domain-independent concepts to support interoperability across fields, and domain ontologies, which capture specialised knowledge for a particular area such as catalysis.
In this way, an ontology represents an explicit and logically interpretable conceptualisation of a domain.
Shared ontologies can therefore support consistent annotation, semantic interoperability, and automated reasoning across independently created datasets and software systems \cite{stuckenschmidt2011ontologien,arp2015building,w3c2012owl2primer}.

The Resource Description Framework (RDF) provides the graph representation model here to represent statements as subject--predicate--object triples \cite{w3c2014rdf11concepts}.
Instance data in such a graph can be typed by linking a resource to an ontology class with \texttt{rdf:type}, while further predicates connect that resource to other instance resources or literal values. Figure~\ref{fig:ontology-grounding-layers} illustrates this schema-instance distinction for catalysis metadata.
Furthermore, the resources and predicates can be identified with Uniform Resource Identifiers (URIs), which allows statements from different sources to refer to the same concept rather than only to local text labels \cite{w3c2014rdf11concepts,huskova2025improvement}.

\input{figures/ontology_grounding_layers}

The Shapes Constraint Language (SHACL) can be used to formalise validation rules for instance data in an RDF graph. A SHACL shape may, for example, require that every catalytic experiment has a catalyst, restrict a temperature value to a numerical datatype, or define how often a particular property may occur.
SHACL therefore evaluates whether the available data conform structurally to the intended representation, whereas an ontology provides the logical vocabulary and axioms used for classification, inference, and semantic interpretation \cite{w3c2017shacl}.

\subsection{Querying and Reasoning}
\label{subsec:querying-reasoning}

Representing metadata as a graph enables information to be retrieved through its semantic structure rather than only through textual similarity.
A graph query describes relations between entities and returns the parts of the graph that satisfy this pattern.
In RDF-based knowledge graphs, such queries are commonly expressed in the SPARQL Protocol and RDF Query Language (SPARQL) as patterns over subject--predicate--object statements \cite{w3c2013sparql11query,w3c2013sparql11overview}.
Property-graph databases use related declarative query languages such as Cypher or the standardised Graph Query Language (GQL) \cite{neo4jCypherManual,openCypherSpecification,iso2024gql}.
Although their underlying graph models differ, both approaches allow data to be retrieved by following explicit connections between entities.

This structural access is particularly relevant for semantic metadata processing.
An extracted term does not have to be treated as an isolated label, but can be examined together with its position in a vocabulary or ontology.
After a candidate concept has been identified, a graph query can retrieve its identifier, preferred and alternative labels, broader concepts, associated classes, or other directly connected semantic information.
The graph therefore provides controlled context for deciding whether a candidate term corresponds to the meaning intended in the source data.
Textual and embedding-based retrieval can support the initial identification of candidates, while graph queries expose the relations required for their subsequent interpretation.

Querying operates primarily on statements that are explicitly present in the graph.
Reasoning extends this access by deriving statements that follow from the semantic model.
Axioms can, for example, propagate class membership through subclass relations or recognise that differently named resources represent equivalent concepts \cite{w3c2014rdfschema,w3c2012owl2primer}.
A query for instances of a general class can consequently also return entities that were only asserted as instances of a more specialised subclass.
Reasoning therefore separates the way knowledge was originally recorded from the level of abstraction at which it can later be retrieved.

Within the workflow developed in this thesis, querying is primarily used to access and inspect the semantic context of vocabulary terms stored in the Neo4j-backed vocabulary layer.
Candidate terms identified from dataset content can be connected to their surrounding graph neighbourhood before they are used for metadata generation.
This allows the extraction process to rely not only on lexical similarity, but also on explicit semantic relations and stable identifiers.
Querying and reasoning thus provide the connection between initially extracted expressions and the controlled domain knowledge against which the resulting metadata are grounded.

\section{Large Language Models}
\label{sec:large-language-models}
Large language models (LLMs) are systems based on neural networks that learn statistical patterns from large amounts of text. They use these patterns to predict the next segment of text in a sequence, and this capability can be used to generate arbitrary outputs, such as queries or even structured RDF graphs. \cite{zhao2026surveyllms,brown2020language}.
The following sections introduce the technical principles most relevant to understanding LLM-based systems, including transformer architectures, retrieval-augmented generation and methods for generating structured outputs.

\subsection{Transformer Architecture}
\label{subsec:transformer-architecture}

Most current LLMs are based on the transformer architecture, which largely replaced the recurrent sequence-processing paradigm with attention-based computation.
Whereas recurrent models process tokens sequentially and summarize preceding information in a hidden state, transformers use self-attention to directly model relationships between positions in a sequence and can perform many of these computations in parallel \cite{vaswani2017attention,zhao2026surveyllms}.
The sequence consists of subunits of text, referred to as tokens, which are mapped to numerical vector representations called token embeddings.
For each token representation, the model computes query, key, and value vectors.
The query of one token is compared with the keys of the permitted token positions to calculate attention weights.
In generative models, causal attention restricts these positions to the current and preceding tokens, thereby preventing the model from accessing later tokens during prediction.
The model then calculates a weighted sum of the corresponding value vectors, producing a context-dependent representation of the token.
For example, in the sentence \textit{The catalyst was tested after \textbf{it} was activated}, the token \textit{it} refers to \textit{catalyst}, and the attention mechanism allows the model to incorporate information from the token \textit{catalyst} when processing the token \textit{it}.
Multi-head attention performs several such attention operations in parallel using different learned projections.
This allows the model to capture several interaction patterns between tokens at the same time.
Each transformer block combines attention with a feed-forward network, while residual connections and layer normalisation support stable information processing.
By stacking multiple blocks, the model progressively refines the token representations.
For generative LLMs, the representation produced at the latest sequence position by the final transformer block is mapped to a score for every token in the model's vocabulary.
These scores are converted into a probability distribution that expresses how likely each token is to follow the preceding context.
The model selects or samples one token from this distribution, appends it to the existing sequence, and repeats the process autoregressively until it generates an end-of-sequence token or another stopping condition is reached.

Transformer models are commonly grouped into encoder-only, decoder-only, and encoder--decoder architectures \cite{zhao2026surveyllms}. Encoder-only models, such as BERT-like systems, process the input bidirectionally and are well suited for representation learning, classification, and span-level tasks \cite{devlin2019bert,zhao2026surveyllms}. Decoder-only models, such as GPT-style systems, generate text autoregressively by predicting the next token from the preceding context and then repeating this step until a complete output has been produced \cite{brown2020language,zhao2026surveyllms}. Encoder--decoder models combine an input encoder with an output decoder and are commonly used for sequence-to-sequence transformations \cite{vaswani2017attention,zhao2026surveyllms}.

The generative behaviour of many LLMs is based on language modelling \cite{zhao2026surveyllms,brown2020language}. During pretraining, the model learns from large text collections with a self-supervised objective, such as predicting missing or subsequent tokens. Although this objective is simple, large-scale pretraining can produce models that capture linguistic regularities, factual associations, and task-like patterns from text \cite{brown2020language,zhao2026surveyllms}. A pretrained model, however, does not automatically behave like a helpful instruction-following assistant \cite{ouyang2022training}. Later training stages therefore adapt the model to user-facing tasks. Instruction tuning trains the model on examples of instructions and desired responses, while reinforcement learning from human feedback can further align outputs with human preferences and task intent \cite{ouyang2022training,zhao2026surveyllms}.

In-context learning describes the ability of large language models to adapt their behaviour from information provided directly in the prompt, without updating the model weights \cite{brown2020language,zhao2026surveyllms}. A prompt may contain a task description, formatting rules, background information, or a small number of examples. The model processes these elements together with the current input as one context and generates a continuation that follows the patterns implied by that context \cite{brown2020language,liu2024lostmiddle}. This makes the prompt an operational part of the model interaction: it can specify what kind of output is expected, how ambiguities should be handled, and which examples should guide the response, while the underlying model parameters remain unchanged.

Text embeddings are also important beyond the internal token representations of a transformer \cite{reimers2019sentencebert}. Encoder models and specialised sentence-transformer models can map words, sentences, paragraphs, or documents into dense vectors that capture semantic similarity \cite{devlin2019bert,reimers2019sentencebert}. Such embeddings make it possible to compare texts by vector distance, cluster related passages, or retrieve semantically similar documents \cite{reimers2019sentencebert,dreger2025knowledgegraph}. They therefore provide a bridge between symbolic text and numerical search procedures, which is one reason why embeddings are frequently used together with retrieval-based LLM systems \cite{gao2023ragsurvey}.

\subsection{Retrieval Augmented Generation}
\label{subsec:retrieval-augmented-generation}

Retrieval-Augmented Generation (RAG) extends a generative language model with an explicit retrieval step \cite{lewis2020retrieval,gao2023ragsurvey}. Instead of relying only on information stored implicitly in the model parameters during training, the system first searches an external collection for relevant documents, passages, database entries, schema descriptions, or examples. The retrieved material is then inserted into the model context, and the model generates an answer conditioned on both the user input and the supplied external evidence \cite{lewis2020retrieval}.

\input{figures/rag_architecture_placeholder}

This separation is conceptually important because model parameters and external knowledge serve different roles \cite{lewis2020retrieval,gao2023ragsurvey}. Parameter knowledge is compressed into the weights during training and is difficult to inspect, update, or restrict after deployment. Retrieved context, by contrast, can be selected at inference time, can reflect a curated or current knowledge source, and can be shown together with the generated response. RAG therefore reduces the need for the LLM to answer purely from memory and gives the generation process access to explicit supporting information \cite{gao2023ragsurvey}.

A common RAG pipeline consists of indexing, retrieval, context construction, and generation \cite{gao2023ragsurvey,zhao2026surveyllms}. During indexing, source documents are split into smaller units and represented for search, often by sparse lexical features, dense embeddings, or a combination of both. During retrieval, the system selects the most relevant units for the current query. These units are then placed into a prompt or context window together with the user's request. The LLM finally generates an output that is conditioned on this retrieved material \cite{lewis2020retrieval,gao2023ragsurvey}. The quality of such a system therefore depends not only on the language model, but also on the relevance, granularity, and ordering of the retrieved context \cite{gao2023ragsurvey,liu2024lostmiddle}.

RAG does not remove all limitations of LLMs \cite{gao2023ragsurvey,asai2024selfrag}. A model may ignore relevant retrieved evidence, overinterpret ambiguous passages, or generate unsupported details if the prompt and validation procedure do not constrain the response sufficiently \cite{liu2024lostmiddle,asai2024selfrag}. Nevertheless, RAG changes the basic information source available to the model: the answer no longer has to be generated only from the statistical associations stored in the parameters, but can be grounded in information supplied at inference time \cite{lewis2020retrieval,gao2023ragsurvey}.

\subsection{Structured Output}
\label{subsec:structured-output}

LLMs generate text token by token, but many downstream workflows require outputs that can be processed as structured data. Structured-output techniques address this by constraining the model interaction before, during, or after generation \cite{schilling2025text,dagdelen2024structured}.

The simplest approach is to specify the desired format directly in the prompt, for example JSON, YAML, XML, Markdown tables, or subject--predicate--object triples \cite{dagdelen2024structured}. The prompt may define fields, allowed values, nesting rules, or examples. However, this only guides the model: the structure is still generated as ordinary text and may therefore be malformed, incomplete, or inconsistent with the requested schema \cite{dagdelen2024structured,caufield2024spires}.

A stronger interface-level approach is tool or function calling \cite{schick2023toolformer,schilling2025text}. Here, the model is asked to select a predefined tool and fill its named parameters. This makes the boundary between natural-language reasoning and machine-readable action more explicit, because arguments can be checked against the tool specification before execution or acceptance \cite{schick2023toolformer,caufield2024spires}. Nevertheless, valid argument structure does not guarantee that the generated values are factually correct or grounded in the input \cite{caufield2024spires,yao2023react}.

A third approach is output parsing and validation \cite{dreger2025knowledgegraph,schilling2025text}. The generated response is treated as a candidate structure and is accepted only if it can be parsed and validated against constraints such as schemas or SHACL shapes \cite{w3c2017shacl,dreger2025knowledgegraph}. This can reject malformed records, enforce required fields, and normalise datatypes. However, validation mainly checks processability; semantic errors can remain when a syntactically valid output contains unsupported or inappropriate content \cite{caufield2024spires,dreger2025knowledgegraph}.
